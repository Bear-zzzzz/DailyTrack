## 五、逐个 JD 要点的完整话术

### 5.1 情景感知（JD #1 🔴）

**弹药：** VLA（项目三）情景感知与安全决策 + LiClaw context engine

**话术：**

> "情景感知我理解有三个维度：**物理上下文**（位置、运动状态、环境噪声）、**设备上下文**（当前 App、网络类型、电量、耳机/蓝牙连接）、**任务上下文**（日程、最近操作、对话历史）。
>
> 物理上下文方面，VLA 项目里我设计了一套多级 Filter，根据主驾驶身份、车门状态、车速、FSD 运行状态等 10+ 维度的传感器数据，动态决定哪些指令可执行。比如行驶中禁用座椅调节，泊车时才能开车门——这不是硬编码的白名单，而是结合车辆状态做的情景判断。
>
> 会话上下文方面，LiClaw 的 context engine 在每轮 LLM 调用前做三件事：从端侧拉取上下文快照、按优先级裁剪（3s 超时降级）、注入 system prompt。这套框架搬到手机上，只是数据源从 CAN 总线变成 Android Sensor API + 系统状态，注入逻辑完全复用。"

**可追问准备——"手机上有哪些上下文你会注入？"：**

> "位置和运动状态（静止/步行/驾车）、当前前台 App（用户之前在干嘛）、日程（接下来有没有会议）、耳机连接（是否在通话/听歌）、网络类型（WiFi/蜂窝/弱网）——这些决定了 Agent 的行为策略，比如弱网时不建议播放在线视频。"

### 5.2 个性化记忆（JD #1 🔴）

**弹药：** LiClaw 记忆架构 + 诊断 Agent 经验库

**话术：**

> "个性化记忆我们做了端云分离的设计——记忆以端侧存储为主，云端同步为辅，按用户 accountId 绑定跨设备跟随。Memory 引擎（SQLite/LanceDB）在容器侧完全关闭，记忆不由 Agent Runtime 管理。
>
> 具体机制上做了两道自动化——auto-recall 在每轮对话开始前，端侧把相关记忆推送到容器注入 Prompt，用后即删不累积 token；auto-capture 在对话结束后，容器把整轮对话回推给端侧做持久化和向量化，再经 LiMesh 同步到云端。容器只做中转桥，不持有记忆。
>
> 这样设计的好处：一是容器可随时销毁重建，记忆不丢失；二是端侧作为记忆主体，隐私数据可控；三是云端副本保证换设备后记忆跟随。
>
> 另外在诊断 Agent 里我也做了经验库的 RAG 检索，用混合检索+rerank 召回历史上类似问题的处理方案，这也是另一种形式的'记忆'——系统级的经验复用。"

**加分准备——三个记忆系统的经典难题：**


| 场景               | 回答                                                                                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **新用户冷启动**   | "首次使用时没有用户记忆，靠场景模板 + 当前上下文兜底。比如'导航回家'——没有记忆时从当前定位和通讯录推断。随着使用次数增加，模板权重下降、个人记忆权重上升。"                         |
| **偏好冲突**       | "比如工作日喜欢简洁回复、周末喜欢详细推荐。记忆不能只存偏好值，要存'偏好 + 触发条件'。召回时根据当前上下文匹配最相关的条件。可以在向量检索时把上下文特征（时间、位置）拼入查询向量。" |
| **记忆时效与遗忘** | "用户上个月常去的地方和这个月可能不同。记忆应该有时效性权重——最近一周的行为优先级高于一个月前的，长期不用的自动衰减。每次 capture 带时间戳，端侧向量存储做衰减。"                   |

### 5.3 端侧模型调用与交互（JD #2 🔴 + #4 🔴 + #5 🔴）

**弹药：** LiClaw Agent Runtime + VLA（项目三）端侧实时性与可靠性 + 诊断 Agent（项目一）ReAct 引擎

**话术：**

> "我参与过模型调用的完整链路——从 Android 端的 ASR 采集到云端推理再到端侧执行，不是只调 API。
>
> 端侧负责三件事：上下文采集和结构化（传感器数据 → JSON → Prompt 注入）、流式回复的接收和渲染（分片缓冲、断句处理）、工具调用的实际执行（从 LLM 的 tool_call 到 Android SDK 的方法调用）。
>
> 举一个完整的调用链路——用户说'打开空调 25°C'，Android 端把 ASR 文本 + 上下文快照（当前车内温度、座椅占用、驾驶状态）通过 WebSocket 发给容器，容器走 Agent Loop 推理出 tool_call，再通过 channel 下发给 Android 端，dc SDK 执行 CAN 指令，结果回传容器做最终回复。
>
> 工具调用分了三条路径：内置 tool 在容器内执行（如 web_search），车辆控制类走 bridge 的 Unix socket 调用 Android SDK（如导航、空调、座椅），对话类走 channel 下发。每条路径有独立的超时和降级策略——工具调用 10 秒、RPC 30 秒、上下文查询 3 秒。
>
> 模型选型上我们接入了理想云的 LLM Gateway，兼容 OpenAI/Gemini 协议。整个调用链路上从 Provider→Model→Agent Runtime→Channel 是可插拔的，换模型不需要改业务代码。
>
> 诊断 Agent 侧用的是标准的 ReAct 范式——Thought → Action → Observation 循环，加上 Domain/Skill/Tool 三层插件化架构。这个引擎我在两个项目中复用了，新业务接入只需要写 Domain 配置和少量 Skill。"

### 5.4 诊断 Agent —— RAG 管线与 Agent 引擎（JD #5 🔴 + #7 🟡）

**弹药：** 诊断 Agent（项目一）——Hybrid RAG 与检索管线、ReAct 引擎、安全护栏

**话术——RAG 管线：**

> "诊断 Agent 的 RAG 管线分五步：意图识别 → 子问题拆分 → 并行混合检索 → Rerank 重排序 → 注入 Prompt。
>
> 首先用小模型判断用户问题是直接回答还是需要检索。需要检索时，小模型先把问题拆成多个子问题，并行发混合检索——代码库走 0.6 全文+0.4 向量各取 10 条，经验库同样权重各取 5 条。
>
> 代码入库前做了预处理：清洗配置/test/demo/SDK 等无意义内容，关键链路做标注。Chunk 策略按文件/模块切分并保留完整函数，每个 chunk 头部注入文件路径、类名、函数名作为前缀——这些 metadata 在 rerank 阶段一并送入模型做语义匹配，不只是裸文本。
>
> 混合检索结果合并后用 8B 模型做 Rerank，阈值设 0.35（该模型上 0.3 视为完全无关）。过滤后的结果注入 Prompt 供大模型推理。
>
> 数据库设计到字段级别：project_id、版本、仓库路径、类名、起止行号、函数名、向量值 blob、chunk_text。Embedding 用 kivy-qwen3-embedding-0_6b。"

**话术——ReAct 引擎与安全控制：**

> "引擎侧用的是标准 ReAct 范式——Thought → Action → Observation 循环。Domain / Skill / Tool 三层插件化架构，Domain 通过配置文件加载可用的 Skill、Tool 和领域 Prompt，新增业务领域只需写配置，引擎零改动。
>
> 安全控制上做了四道防护：工具白名单校验，shell脚本路径，命令黑名单正则校验，工具执行护栏：超时时间，输出长度截断；工具重复调用检测，连续失败熔断降级
>
> RAG 部分做了两套：一套是排查经验库（经验级 RAG），一套是版本化代码库（代码级 RAG）。 用 FTS5 BM25 + 向量余弦的 hybrid 检索
>
> 每个工具调用产生一条不可变事件，追加到表里；每轮执行后，都把完整的状态，写到check point json里。崩溃恢复后，都支持从最近的check point 做增量重放
>
>
> 最终效果：诊断耗时压缩到 15 分钟，自动化排查率 75%，人工采纳率 80%+，累计处理 200+ 真实工单。"

### 5.5 架构可维护性

**弹药：** Domain/Skill/Tool 三层架构 + LiClaw Skill 配置化

**话术：**

> "我做 Agent 架构时最关注的是扩展性——不能每加一个功能就改引擎代码。
>
> 诊断 Agent 里我设计了 Domain / Skill / Tool 三层——Domain 是业务场景的配置文件（定义可用 Skill + 指引 Prompt），Skill 是可复用的能力单元（比如日志采集、代码检索），Tool 是原子操作。新增一个业务领域只需写配置文件 + 选择已有 Skill，核心引擎零改动。
>
> LiClaw 里有同样的思路——30+ 车辆 Skill 的 function schema 全是 JSON 配置文件，运行时动态加载，新增一个 Skill 只需定义 schema + Android 端实现，引擎代码不动。
>
> 放到手机助手上——新增一个'帮我点外卖'的能力，只需要定义工具 schema + 写 Android 端执行逻辑，Agent 引擎完全复用。"

### 5.6 端侧性能优化（JD #6 🟡）

**弹药：** LiClaw 流量治理 + VLA 弱网策略


| 场景     | 策略                        | 参数/效果                   |
| -------- | --------------------------- | --------------------------- |
| 连接层   | Unix Domain Socket 代替 TCP | 零拷贝、不经过协议栈        |
| 心跳     | 10s 心跳测活                | 车机 ANR 后黑窗从 30s→~10s |
| 超时降级 | 差异化超时                  | RPC 30s / CE 3s / Tool 10s  |
| 流式分片 | ~50 字符加权断句            | 中英日标点处切分            |
| 死锁保护 | 5min 看门狗                 | 崩溃后自动回 idle           |
| 弱网兜底 | 无回执→fail                | 避免长时间等待 ANR          |
| 内存     | 容器无状态                  | 记忆/状态不驻留容器         |
| 并发     | session 级排队互斥锁        | 单用户场景可靠              |

**话术：**

> "通信层——我们选了 Unix Domain Socket 而不是 TCP localhost。容器和 Android 在同一台设备上，Unix socket 不经过 TCP/IP 协议栈，内核直接内存拷贝，性能更好。
>
> 实时性——心跳设了 10 秒。车机上 ANR 恢复后 TCP 连接可能还显示 OPEN，必须靠心跳才能发现断连。我们把心跳从默认值调到 10 秒，把用户感知的黑窗从半分钟压到了约 10 秒。流式回复做了 ~50 字符的分片缓冲，在中英日标点处切。
>
> 稳定性——5 分钟死锁看门狗，Agent 崩溃导致 busy 状态卡死时，超时自动回 idle 并通知端侧恢复。session 级别的互斥排队锁保证同一用户不会同时触发多个 Agent 循环。
>
> 弱网场景——VLA 项目里没收到 AD 状态回执，直接返回 fail 指令，不做无限等待。放到手机上可以做更精细的分级——WiFi 下大模型、蜂窝下小模型、弱网走本地规则。"

**JD 五维度补充回答（如果面试官逐条追问）：**


| JD 维度                 | 话术                                                                                                                    |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------- |

| **内存管理**            | "容器无状态设计——记忆、session 状态都不在容器内驻留。Android 端中间层只持有轻量级状态快照，大对象序列化后即释放。"    |
| **电量消耗**            | "事件驱动而非轮询——只在系统广播时激活。心跳平衡灵敏度和功耗。手机上可做分级——灭屏/低电量模式下降频或切本地小模型。" |

### 5.7 端到端评测工具建设（JD #3 🟡）

**弹药：** 评测平台（项目二）

**话术：**

> "我对评测体系的理解是——它不是跑分工具，而是 Agent 迭代的发动机。
>
> 我搭的评测平台做了三件事：
>
> 一是多维覆盖——把任务质量拆成了 4 级 13+ 指标（协议准确率、呈现准确率、拒绝合理性、体验质量）。每个指标有独立的校验逻辑。
>
> 二是三级漏斗校验——代码规则判明确错误（如必填字段缺失），LLM 语义判模糊场景，人工复核兜底。
>
> 三是自动化闭环——异步并发跑全量回归，从天级缩到分钟级；Bad Case 自动归因到 Prompt/流程/RAG；设 Gate 拦截不达标版本。核心必过集守住基线，盲测集做 unbiased 评估。
>
> 评测不只是'测 Agent'——模型训练出新版本 → 评测平台跑全量回归 → 多维指标对比 → Bad Case 归因反馈给训练侧（是 Prompt 要调、还是 SFT 数据要补、还是 RAG 召回有问题）→ 训练侧修正 → 再次回归。我在理想做的评测平台覆盖了这个闭环的后半段，前半段模型训练我没有直接参与，但理解全流程，知道评测结果怎么反哺训练。"

## 七、Q&A 合集

**Q1: 车机 Agent 和手机 Agent 最大的区别是什么？**

> "传感器维度和交互频率。车机传感器相对固定（车门、车速、空调用），交互频率低；手机传感器更丰富（位置、App 状态、通知、耳机），交互随时打断。但底层的 Agent 架构——上下文注入、工具调用、记忆管理——是通用的。区别在于上下文维度的丰富度和并发/打断的处理。"

**Q2: 手机端内存很紧张，模型推理怎么放？**

> "两个思路。一是云端推理+端侧执行，像我们车机上容器跑在云端 Gateway、Android 只做工具执行。二是端侧用小模型做意图分发和简单决策，复杂推理走云端——当年我们在诊断 Agent 里就是小模型做意图识别+问题拆分，大模型做最终推理。手机端完全可以用类似的端云分级策略。"

**Q3: 你怎么理解"个性化记忆"？**

> "不是存对话记录。是提取偏好、习惯、关系——比如用户常设 25°C 空调、通勤路线偏好、喜欢简洁的回复风格。技术上分 recall（注入相关记忆到 Prompt）和 capture（从对话中提取新的偏好写回记忆库）两步，我们 LiClaw 里已经落地了这套 auto-recall/capture 机制。"

**Q4: 手机上常驻 Agent 服务怎么控制电量？**

> "几个策略。一是事件驱动而非轮询——只在系统广播（通知、App 切换、语音唤醒）时激活，不持有 wakelock 做后台循环。二是分级响应——亮屏+WiFi 时走完整云端推理，灭屏+蜂窝时降级为本地小模型或只做通知聚合。三是批量处理——多条通知攒一批再触发一次推理。参考 Android Doze 模式的适配思路。"

**Q5: 如果用户在开车，手机助手的行为策略应该怎么调整？**

> "检测到驾驶模式（速度 > 20km/h 或连接车载蓝牙）后，策略切换：回复改语音优先、减少文字展示、屏蔽需要视觉交互的功能、简化交互为单轮问答而非多轮对话。这些策略作为 context tag 注入 Prompt，让模型自适应——和 VLA 项目里根据车速/驾驶状态动态调整指令策略的思维完全一致。"

**Q6: 端侧模型和云端模型怎么分工？**

> "分三层。端侧轻量模型做实时性要求高的——意图分类、实体提取、敏感内容过滤、简单指令执行。云端大模型做复杂推理——多步任务规划、知识问答、内容生成。中间加一层路由器——根据 query 复杂度和当前网络/电量动态选路。这和诊断 Agent 里'小模型做意图识别和问题拆分、大模型做最终推理'是同一套端云分级思想。"

---

> **核心叙事：** 车机端侧 Agent + 评测闭环 → 手机端侧 Agent。不是转行，是同一赛道换设备。
