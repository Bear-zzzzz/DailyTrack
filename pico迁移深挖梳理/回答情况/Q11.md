## 参考素材（待核实并转成自己的回答）

**口述参考回答：** 把变化点抽象为接口，让业务实现放在独立子包，通过注册表和装配器注入核心引擎，避免业务直接修改主循环。项目采用统一 Plugin 接口、声明式注册和编译期集成；二期规划进一步扩展到 AgentLoop、Channel、Provider 等。进程内模块化可以减少调用开销，但仍要明确依赖、调用顺序、错误策略和并发边界。它本身不等于隔离沙箱，阻塞或 panic 是否可隔离需要另外设计。

**材料依据：** S：一期组件化及二期全域插件化；R：一期工程体系。

**待补充：** 必须补：一期实际接口、注册顺序、冲突检查和错误处理；沙箱实现未核实。

**继续追问：** 注册表如何避免顺序不确定？一个插件阻塞会影响谁？

## 补充校准：原生扩展点与项目新增能力

已核对官方 README/Hooks 文档及本机 fork 的业务插件层。PicoClaw 已有工具注册、Hooks、Skills/MCP 等能力；项目新增的是统一业务 Plugin 接口、注册 API 与编译期接入、启动期装配层。不能将已有扩展点都算成项目从零建设，也不能因上游有 Hooks 就说项目插件层只是现成功能。

本机接口包含 `Meta()` 与 `Register(api)`，API 统一转接 Tool/Hook 注册并提供配置、工作区和 Bridge。使用 `init()` 和匿名导入接入、启动时 `Assemble` 装配，不是 `.so` 动态加载；完整服务生命周期和全域插件化仍需按当前实现与二期规划分别说明。

详细依据见 [素材依据中的插件能力校准](../素材依据.md)。个人实际承担的接口与装配代码仍待进一步确认。
