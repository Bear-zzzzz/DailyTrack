## 使用范围与回答口径

本文覆盖上一份索引的 **21 个高频主题、80 组代表性问答**。部分相近问法合并，部分补充必要追问；**不是对 1,581 次问项逐条作答**，不把新增解释回填成作者原题。原文简写或含混之处先说明假设，不补造确定题意。

- **协议/规范事实**：以来源标记中的正式规范、公开标准草案或官方文档为依据，适用范围与版本写明。NIST SSDF 是安全开发框架；项目里的 Harness、Skill、OpenSpec、Superpowers 不是统一的强制行业标准。
- **工程建议**：文中“建议”“参考链路”“取舍”是基于上述原理整理的设计方案，不是软件自带保证。参数、QPS、超时与重试次数需要按业务压测确定。
- **个人项目回答**：可以采用口述模板，但必须换成自己的实际职责、规模、数据和失败案例；没有量化实验就明确说没有，不背本案例当作个人经历。
- **来源标记**：`[Sxx]`、`[Bxx]` 均可在来源文档查到主来源地址；基础算法/概率题直接给出假设与推导。协议文档引用不同版本用于解释边界，不意味着旧版就是核对日的最新版。

推荐口述顺序：**先结论 → 讲机制/流程 → 讲边界和取舍 → 给自己的证据**。不要只堆框架名称，也不要把“自动化流程跑完”说成“业务已验证正确”。

## 对照已有笔记，需要校准的三点

已结合项目内的上下文工程、RAG 工程和面试问答笔记；其中的方法可作为经验参考，但不能直接当成统一规范：

1. [上下文工程笔记](../../Week9_Interview/Dailies/2026-05-19_Day1_Context_Engineering.md) 中的“可信度顺序”应拆开：**指令优先级、事实证据可信度、真实授权**不是同一排序。高优先级指令不改变事实，工具文本不能自行授予权限。
2. [RAG 工程笔记](../../Week9_Interview/Dailies/2026-05-20_Day4_RAG_Engineering.md) 中的检索指标，需要明确分母：**Recall@K 看相关资料被找回多少，Precision@K 看结果里相关项占多少**，不能混用。
3. [已有面试问答](../../简历相关/面试问答梳理.md) 中的融合权重、阈值、最大轮次和模型自评置信度属于具体设计/待验证数据；不是跨模型通用参数，也不能替代独立验收证据。

本次仅在新答案中澄清这些边界，未改写原始笔记或已采集题库。

## 1. AI 编程与规范驱动开发

对应原题：P001「怎么保证 ai 改代码不影响其他模块」「怎么用 agent 提效」；P002「pi 和 opencode 区别」「openspec 平时怎么使用」「superpowers 的 skill」。

<a id="q1-1"></a>

### Q1.1 AI 改代码怎样降低对其他模块的影响？

**口述答案：**我不会只靠 Prompt 约束。我会把变更范围、接口契约、业务不变量、测试和发布权限放到工程流程里，让 AI 在受限工作区完成变更，独立验证后才进入发布。

建议分六道检查：需求/验收标准明确 → 依赖和影响面分析 → 分支或工作区隔离 → 静态检查及单元/契约/集成测试 → 独立审查 → 灰度与回滚。特别保护鉴权、事务、公共接口和数据库迁移；用 diff 检查阻止越界改文件、删除测试或降低断言。

**追问：AI 为通过测试改了业务逻辑怎么办？**测试本身要有可信来源，需求负责人维护验收条件；开发 Agent 无权同时改验收标准和批准上线。增加真实回归案例、属性测试和人工审查。测试通过是风险证据，不是“绝不会影响其他模块”的证明。[S02](05_参考来源与版本说明.md#s02)[S06](05_参考来源与版本说明.md#s06)

<a id="q1-2"></a>

### Q1.2 SDD、TDD、BDD 与 OpenSpec 分别解决什么问题？

**口述答案：**SDD 先明确做什么及约束，TDD 用失败测试驱动实现，BDD 用业务可理解的场景对齐预期；它们互补，不是装了一个插件就自动实现。

- SDD：需求、接口、非目标、异常路径、验收标准可追溯，规格随变更维护。
- TDD：先写测试并观察正确的失败，再最小实现，最后重构；避免只给现有实现补“必然通过”的测试。
- BDD：用 Given/When/Then 描述业务行为，但格式本身不保证测试有效。
- OpenSpec：本次核对的官方 README 展示 proposal、specs、design、tasks，以及实现后归档合并规格的工作流。具体命令随版本变化，面试重点讲产物和决策，不背固定命令。

**取舍：**小修复可以轻量化，大接口变更和跨模块需求需要更完整规格。过期规格会误导 Agent；应给规范负责人、版本、变更关联与失效检查。[S06](05_参考来源与版本说明.md#s06)

<a id="q1-3"></a>

### Q1.3 Harness 是什么？Skill 能保证 Agent 严格执行规范吗？

**口述答案：**Harness 在这里指模型外围的运行与约束机制，包括工具接口、上下文组织、权限、预算、验证和停止条件；这个术语没有统一强制实现标准。Skill 主要告诉 Agent 如何做，硬约束必须由运行时执行。

例如文本可以写“测试通过才发布”，但真正的发布接口应检查有效测试记录、版本、审批人与目标环境。日志里记录“已审批”不等于审批成立；模型自行声称“完成”也不等于交付成立。

**Superpowers 怎样回答？**按本次核对的技能体系，可以举需求澄清、规划、TDD、系统化调试、代码审查和完成前验证等流程技能，再讲在哪个任务用了哪个技能、产物是什么。它是项目的软件开发方法，不是行业强制标准，不能用“有 Superpowers”代替质量证据。[S09](05_参考来源与版本说明.md#s09)[S02](05_参考来源与版本说明.md#s02)

<a id="q1-4"></a>

### Q1.4 Pi 与 OpenCode 怎么比较？各自技术难点是什么？

**口述答案：**先限定我读过的版本，再从执行循环、会话状态、扩展机制、工具权限和客户端接入比较，不直接给“谁更强”的结论。

本次读取的 Pi README 把它定位为可扩展的 Agent Harness，支持 extensions、skills、RPC 和 SDK；README 明确基础发行不默认包含 sub-agent、plan mode 等功能，可由扩展补充。OpenCode 当前 API 文档展示实验性的 HTTP API 服务接口；官方 V1 Server 文档则展示 HTTP 服务/OpenAPI 的客户端接入模式。比较时分别引用对应版本，不能把 V1 参数或行为套到 V2。

**通用难点：**流式输出与工具事件顺序、取消传播、会话恢复、并发写冲突、插件副作用、密钥隔离、升级兼容和可观测性。选轻量可嵌入内核还是多客户端平台，要看团队集成成本和治理需求。没有读过实现细节就说“只验证了文档和运行行为”，不要声称完整读过源码。[S07](05_参考来源与版本说明.md#s07)[S08](05_参考来源与版本说明.md#s08)[S24](05_参考来源与版本说明.md#s24)

## 2. 模型效果、幻觉与评测

对应原题：P004「好的 AI 项目」；P007「Agent 凭什么能做到」「运维效率有具体数据吗」；P009「幻觉怎么解决」；P010「提效率是多少」。

<a id="q2-1"></a>

### Q2.1 大模型幻觉如何降低？能不能彻底消除？

**口述答案：**不能承诺彻底消除。先区分事实错误、无证据推断、错误调用工具和虚假完成，再分别用检索、约束、执行证据和评测降低风险。

事实问答要求可访问的证据和引用；不足时澄清或拒答。结构化输出做 schema/范围校验。操作型任务以真实工具结果和业务后置条件验证，而不是相信一句“执行成功”。高风险动作要独立权限校验和审批。

**取舍：**RAG 只提供证据，不能保证模型忠实使用；多 Agent 互相同意也可能一起犯错。应在独立测试集统计无依据回答率、任务成功率、错误操作率与拒答质量，同时记录成本和延迟。[S01](05_参考来源与版本说明.md#s01)[S05](05_参考来源与版本说明.md#s05)

<a id="q2-2"></a>

### Q2.2 怎样构建 Agent 评测集？为什么不能只让另一个 LLM 打分？

**口述答案：**先定义可观察的成功条件，再按真实任务分布建数据集；客观检查优先，模型评分补充语义维度，人工抽检校准。

样本覆盖正常任务、模糊需求、权限不足、旧文档、工具超时、依赖失败、攻击文本和长任务。开发集用于调参，保留集用于比较，不能边调边把答案泄露给被测系统。分别测最终交付、关键轨迹、工具选择、参数正确性、恢复能力、延迟和成本。

事实/数值/代码行为用规则或执行测试验证；语义评分制定 rubric，做盲评与人工一致性检查，避免位置偏好和同模型偏差。失败案例回流，但不要把回流后的训练内成绩当作泛化能力。上线后还要监控分布变化。[S01](05_参考来源与版本说明.md#s01)

<a id="q2-3"></a>

### Q2.3 AI 提效怎样量化？面试没有真实数据该怎么说？

**口述模板：**“我把提效拆成吞吐、交付周期、人工投入、质量和成本。在相近任务复杂度下比较基线组与 Agent 组，同时记录人工审核、返工与线上问题，而不只计算代码生成速度。”

可以定义：

- 人工时间节省率 = `(基线人工分钟 − Agent方案总人工分钟) / 基线人工分钟`。
- 无人完成率 = `无人工介入且通过验收的任务数 / 纳入测量的任务数`。
- 单次有效交付成本 = `(模型、计算、审核、返工等成本) / 验收通过任务数`。
- 运维看 MTTR、有效告警占比和误报率，不能只靠减少告警数量判断优化成功。

**没有数据时：**明确“目前有案例验证，没有完成受控对比，所以不报百分比”。说明准备如何采样和测量。每分钟省了多少、QPS 是多少、薪资涨幅是多少都必须来自自己的证据。[S01](05_参考来源与版本说明.md#s01)以上公式是本回答建议的测量口径，不是统一行业公式。

<a id="q2-4"></a>

### Q2.4 人都做不到，Agent 凭什么做到？如何评价一个“好的 AI 项目”？

**口述答案：**Agent 可以扩大检索范围、自动调用工具、并行处理标准化步骤，解决人工时间或信息覆盖的瓶颈；但缺少信息、权限或可执行流程时，它不能凭空做到。

评价项目看用户问题、原流程基线、可验证收益、错误成本、人工兜底、成本可持续性和部署维护。面试举自己实际用过的项目，讲一条完整任务链与一个失败案例，别只列热门项目名。[S01](05_参考来源与版本说明.md#s01)[S11](05_参考来源与版本说明.md#s11)

<a id="q2-5"></a>

### Q2.5 怎么选模型，成本和延迟如何优化？

**口述答案：**先用真实任务集筛选满足质量、权限、数据驻留和延迟要求的候选，再比较单次有效交付成本；不能按参数量或排行榜直接选生产模型。

不同任务可路由到不同模型，但必须测路由误差和回退成本。先减少无关上下文、重复调用和不必要工具循环，再评估缓存、并发、批处理和推理参数。缓存必须包含模型/Prompt/知识/权限版本，不能跨租户复用敏感结果。

TTFT、完整任务耗时、P95/P99、错误率和每个验收通过任务的总成本一起看。所谓“小模型便宜”可能被更多重试和人工返工抵消；具体模型名、API 能力与价格按所用版本另核实。[S01](05_参考来源与版本说明.md#s01)[S11](05_参考来源与版本说明.md#s11)

## 3. Agent 架构与完整执行链

对应原题：P001「agent runtime」；P002「框架」；P004「自然语言到结果详细流程」；P005「完整调用链」；P010「Agent 构成」。

<a id="q3-1"></a>

### Q3.1 从用户自然语言到最终结果，完整链路怎样设计？

**口述答案：**入口完成身份和任务校验，整理目标与上下文，再由规划/决策模块选择动作；运行时检查权限并调用工具，收集结果、验证后置条件，继续执行或结束。

参考链路：身份/租户 → 需求澄清 → 上下文检索 → 计划或下一动作 → 策略检查 → 工具执行 → 结构化结果 → 验证/反馈 → 完成、转人工或失败。任务 ID、步骤 ID、证据来源、版本和预算贯穿全链路。

**关键区别：**模型提出动作，运行时决定动作能否执行；回答生成与真实业务副作用不是同一件事。输出不仅有自然语言，还应有交付物、状态、证据与未完成事项。[S11](05_参考来源与版本说明.md#s11)[S03](05_参考来源与版本说明.md#s03)

<a id="q3-2"></a>

### Q3.2 Agent Runtime 应该负责什么？断点恢复存什么？

**口述答案：**Runtime 管执行生命周期，不只是包一层模型 API。它管理任务状态、模型和工具适配、超时取消、权限、预算、并发、持久化、审计和恢复。

建议显式状态包括 queued、running、waiting_approval、succeeded、failed、cancelled。Checkpoint 记录任务/节点版本、已确认输入输出、待执行动作、工具请求标识、预算、产物引用和必要上下文；大文件用对象引用，不全塞会话文本。

**追问：恢复后会不会重复扣款或发消息？**恢复不等于副作用恰好一次。要依靠幂等键、执行台账、结果查询或业务补偿确认前次动作；无法确认的高风险操作转人工，而不是盲目重放。[S10](05_参考来源与版本说明.md#s10)

<a id="q3-3"></a>

### Q3.3 ReAct、Plan-and-Execute、Workflow 如何取舍？

**口述答案：**路径明确的环节优先确定性 Workflow；需要根据中间结果探索时用循环式决策；可提前拆解且步骤依赖较清晰时用计划加执行，并允许校验后的重规划。

ReAct 类模式强调决策与观察交替，灵活但容易多轮消耗；Plan-and-Execute 利于预算和依赖管理，但初始计划可能错误；Workflow 易审计，但过度固定会处理不了新情况。它们可以组合，不是三选一。

**停止条件：**验收通过、不可恢复错误、权限不足、用户取消、预算/轮次耗尽、重复无进展。应依赖可验证状态，不把“模型说完成”或“自信超过某百分比”当唯一退出条件。[S11](05_参考来源与版本说明.md#s11)

<a id="q3-4"></a>

### Q3.4 Agent 框架了解哪些？怎样证明不是只会背名字？

**口述模板：**“我按显式状态图、工具循环和产品型编排平台理解框架；我实际使用过的是〔如实填写〕。重点比较持久化、人工审批、重试语义、上下文隔离、扩展接口与生产可观测性。”

例如 LangGraph 文档提供状态与持久化能力，但内存 checkpointer 不代表重启后可恢复。框架选型应从最小端到端验证开始：中断恢复、重复执行、取消、并发和权限失败都要测试。不要因为框架提供某组件，就认为集成后的系统自动满足可靠性或安全要求。[S10](05_参考来源与版本说明.md#s10)[S11](05_参考来源与版本说明.md#s11)

## 4. MCP、Tool、Skill 与协议

对应原题：P001「tool 成功但没效果」「tool 和 MCP」；P002「Superpowers skill」；P004「MCP 如何设计」；P010「MCP 和 Skill」。

<a id="q4-1"></a>

### Q4.1 Tool、MCP、Skill、Function Calling、CLI 分别是什么？

**口述答案：**Tool 是可执行能力，Function Calling 是模型表达工具调用意图的机制；MCP 是连接客户端与能力服务的协议；Skill 是任务方法和可复用知识/脚本的组织；CLI 是命令行调用方式。

它们处在不同层：Skill 可以指导调用 Tool，Tool 可以经 MCP 暴露，也可以由进程内函数或 CLI 实现。MCP 还有资源、提示等能力，不能简化成“远程函数”或“提示词集合”。Skill 的具体文件格式和生命周期由平台定义，并不是一套放之四海皆准的协议。

**追问：用了 MCP 是否自动安全？**否。协议接口、用户授权、服务端鉴权、工具权限与实际业务权限要分别落实。A2A 类协议也不能替代业务状态和授权设计。[S03](05_参考来源与版本说明.md#s03)[S04](05_参考来源与版本说明.md#s04)[S05](05_参考来源与版本说明.md#s05)

<a id="q4-2"></a>

### Q4.2 如何设计一个可维护的 MCP 服务？

**口述答案：**从业务能力而不是数据库表设计接口。每个工具定义清晰输入输出、前置条件、错误分类、权限与副作用，并把敏感校验放在服务端。

本次核对的 2025-11-25 tools 规范给出 `tools/list`、`tools/call`、输入 schema 和工具执行错误 `isError` 的机制。实现上建议增加资源范围限制、超时、大小上限、幂等键、审计、脱敏和版本兼容；不要暴露任意 SQL、任意 shell 作为普通业务工具。

**版本边界：**MCP 持续演进，不能把某版初始化流程、字段或传输方式说成永久规则。实际部署固定兼容版本与 SDK，并测试客户端/服务端组合。[S03](05_参考来源与版本说明.md#s03)[S04](05_参考来源与版本说明.md#s04)[S05](05_参考来源与版本说明.md#s05)

<a id="q4-3"></a>

### Q4.3 Tool 显示成功，但业务没有生效，如何排查？

**口述答案：**先分清传输成功、协议成功、工具成功和业务成功。HTTP 200 或函数返回不抛异常，不能证明写入已经生效。

按请求 ID 追踪：参数和目标环境是否正确 → 权限/租户是否匹配 → 工具结果是否有业务错误 → 操作是同步还是返回了异步任务 ID → 事务是否提交 → 读到的是缓存、副本还是错误环境 → 业务后置条件是否成立。

写接口应返回可查询的对象/操作标识，异步任务明确 pending/failed/completed，最终读回或订阅结果验证。重试前确认前次是否已执行，避免“以为失败”造成重复副作用。[S04](05_参考来源与版本说明.md#s04)[S19](05_参考来源与版本说明.md#s19)排查顺序是工程建议，不是 MCP 强制流程。

<a id="q4-4"></a>

### Q4.4 Skill 多、相似或互相冲突怎么办？

**口述答案：**先治理定义与生命周期，再优化召回。每个 Skill 写清适用/不适用场景、输入、输出、前置条件和示例，元数据先召回，详细内容按需加载。

相似能力合并或增加反例；用路由评测集衡量误选/漏选，不根据 description 相似度直接执行。固定版本、负责人、签名/审核、弃用和回滚，任务记录加载了哪个版本。

**冲突谁优先？**指令权限、业务事实和操作授权是不同维度。高优先级指令不改变数据库事实；工具输出也不能升级成系统指令。证据冲突时看来源、时间、适用范围并澄清，不能笼统规定“MCP 永远比知识库可信”。[S03](05_参考来源与版本说明.md#s03)[S05](05_参考来源与版本说明.md#s05)[S09](05_参考来源与版本说明.md#s09)

## 5. 算法与概率

对应原题：P008「每月第一天是星期一」「两个孩子至少一个女孩」；P013「三数之和」；P017「令牌桶」；P020「全排列」。以下给出标准假设下的解题方法，不声称补全作者遗漏的题干。

<a id="q5-1"></a>

### Q5.1 两个孩子，至少一个是女孩，两个都是女孩的概率？

**答案：**先约定两个孩子的性别独立、男女等概率，且给出的条件只是“至少一女”。有序样本为男男、男女、女男、女女；排除男男，剩下三个等概率事件，答案为 `1/3`。

**常见陷阱：**如果条件是“随机看到其中一个孩子，并且她是女孩”，或明确“大孩子是女孩”，样本筛选机制不同，不能自动套 `1/3`。面试先问清观察方式，再用 `P(女女 | 至少一女)` 求解。这里属于基础条件概率推导，不依赖具体软件规范。

<a id="q5-2"></a>

### Q5.2 一个月第一天是星期一的概率是不是 1/7？

**答案：**若题目简化为七种星期等概率，答案是 `1/7`。但真实公历月份不能未经约定就假设均匀。

按“在一个完整公历 400 年周期的 4800 个月中等概率选一个月”计算，星期一开头的月份为 684 个，概率 `684/4800 = 57/400 = 14.25%`，并非严格 `1/7`。本次用 JavaScript UTC 日期遍历 2000—2399 年验证；其他采样范围要重新计算。

**面试要点：**先明确样本空间，不直接把直觉当概率。这个结果是明确历法与采样假设下的计算，不是原题已给出的条件。

<a id="q5-3"></a>

### Q5.3 三数之和如何实现并去重？

**答案：**排序后枚举第一个数，剩余区间用双指针。目标常见为零，但以题目给定 target 为准。和小于 target 移左指针，大于则移右指针；命中后记录并跳过重复左右值，同时跳过重复的第一个数。

复杂度：排序 `O(n log n)`，扫描总计 `O(n²)`；额外空间要区分排序实现、结果空间和辅助工作区，不能一概承诺 `O(1)`。注意宽整数求和、防止越界，以及题目是否要求修改原数组。

**测试：**空数组、少于三项、全零、重复解、无解、极值。去重必须按值组合，不是仅检查索引是否相同。这里是标准双指针推导。

<a id="q5-4"></a>

### Q5.4 令牌桶与漏桶有什么区别？线程安全怎样保证？

**答案：**令牌桶以速率 `r` 补充令牌，最多 `B` 个；每次请求消耗相应令牌。可以容许受 `B` 限制的突发。以固定出队速率整形的漏桶强调平滑输出；实际产品的“漏桶”实现可能用于计量拒绝，需确认语义。

按需补充公式：`tokens = min(B, tokens + elapsed × r)`。用单调时钟，补充、检查与扣除作为同一原子临界区；不要每次只补充却忘了同步更新时间。分布式实现还要定义时钟来源、原子操作、租户 key 和故障时放行/拒绝策略。

**取舍：**本地桶吞吐高但多实例总额度会放大；共享桶便于统一配额但增加网络依赖。限流只能控制入口，不替代队列长度、并发和超时保护。这是通用计量算法设计，参数需按业务测量确定。

<a id="q5-5"></a>

### Q5.5 全排列如何实现？有重复值怎么办？

**答案：**回溯维护当前路径及已使用元素，长度达到 `n` 时复制结果。包含重复值时可先排序，在同层跳过“相等且前一个相同元素尚未使用”的分支，避免输出重复排列。

输出 `n!` 个长度为 `n` 的排列，材料化全部结果通常需要 `O(n × n!)` 时间与结果空间；辅助递归和路径约 `O(n)`。不能说完整枚举只有 `O(n!)` 且“空间 O(1)”而忽略输出。

先确认要按值去重还是把不同索引当不同元素；大 `n` 应讨论生成器、分页或只求计数。这里是回溯与输出规模的推导。

## 6. Agent 记忆与上下文管理

对应原题：P017「Agent 之间上下文丢失」；P019「用户级 Memory」；P025「memory」；P026「上下文管理」；P027「Harness 上下文」。

<a id="q6-1"></a>

### Q6.1 Memory 和 Context 有什么区别？如何分层？

**口述答案：**Context 是本次模型调用可见的信息，Memory 是跨调用或任务可检索的持久信息。两者不是同一个存储，也不应该把所有长期记忆每轮全注入。

建议分：当前工作状态、会话摘要、用户偏好、经过确认的任务经验、团队知识。记录来源、时间、版本、有效期和租户/用户范围；用户偏好与团队事实不能混为全局记忆。KV Cache 是模型推理加速状态，也不等于业务 Memory。

记忆写入需要规则或质量检查，删除与更正可传播。工具输出、攻击文本和未经确认的模型猜测不能自动变成持久事实。[S10](05_参考来源与版本说明.md#s10)[S05](05_参考来源与版本说明.md#s05)

<a id="q6-2"></a>

### Q6.2 长上下文如何压缩而不丢关键信息？

**口述答案：**先管理信息类型，再压缩文本。保留目标、约束、授权状态、关键证据、已完成动作、未决问题和产物引用；冗长日志与原文移到外部存储，按需读取。

摘要要带原始证据引用，重要标识和数值尽量结构化保存。按预算增量压缩，同时用任务评测检查约束保留率、事实错误和恢复后成功率；别认为“摘要更短”就是优化。

**追问：压缩后 KV Cache 是否有效？**取决于模型服务的前缀缓存实现、缓存键和变更位置。改动前缀通常减少可复用范围，不能承诺所有后端都保留或全部失效。稳定规则放在稳定前缀，动态证据放后部是一种设计选择。[S10](05_参考来源与版本说明.md#s10)[S01](05_参考来源与版本说明.md#s01)

<a id="q6-3"></a>

### Q6.3 多 Agent 上下文如何传递？怎样处理“失忆”？

**口述答案：**不默认共享全部聊天历史，使用明确任务契约传递目标、输入版本、约束、证据引用、产物和状态。共享可审计事实，隔离各角色临时探索。

关键状态持久化并带版本，用摘要加可读取原文避免二手摘要层层失真。失败恢复先恢复任务状态，不靠模型回忆“上次大概做了什么”。用户说的是新意图时澄清是否结束旧任务，不能仅定时清空会话。

**边界：**协作访问受真实权限控制；“两个 Agent 属于同一团队”不是共享所有用户数据的理由。[S10](05_参考来源与版本说明.md#s10)[S05](05_参考来源与版本说明.md#s05)

## 7. 多 Agent 协作、路由与通信

对应原题：P004「Leader 拆任务选成员」；P010「分工」；P013「Agent Team」；P016「单 Agent、多 Agent、Workflow」；P017「上下文丢失」。

<a id="q7-1"></a>

### Q7.1 为什么用多 Agent，不用一个大 Agent？

**口述答案：**只有角色分工、独立权限、可并行子任务或不同上下文边界确实带来收益时才拆。简单任务一个 Agent 加工具常常更容易维护。

多 Agent 有分工和并行优势，但增加通信、状态同步、Token、延迟和排错成本。先有单 Agent 基线，再做消融比较；不要把 Agent 数量当先进程度。

典型拆分可以是需求分析、实现和独立验证；可验证的流水线用固定编排，开放任务才让调度 Agent 动态派发。共享目标不意味着验证者必须相信开发者的结论。[S11](05_参考来源与版本说明.md#s11)[S01](05_参考来源与版本说明.md#s01)

<a id="q7-2"></a>

### Q7.2 Leader 怎样拆任务、路由并处理子 Agent 失败？

**口述答案：**先按交付物、依赖与权限拆解，再根据能力注册表、可用性、任务负载和成本选择执行者。模型可推荐路由，但执行前由规则校验能力和权限。

任务契约建议包含 task_id、输入/代码版本、允许范围、验收条件、deadline、预算和依赖。完成以产物加证据确认，不以自由文本“好了”确认。子任务失败分类后重试、换执行者、缩小范围或转人工；重复派发要幂等。

**Leader 挂了：**任务与完成台账持久化，恢复后核实已完成节点，再接续；如果采用选主/租约，要防止旧 Leader 继续写。框架恢复能力不替代业务副作用处理。[S10](05_参考来源与版本说明.md#s10)[S11](05_参考来源与版本说明.md#s11)

<a id="q7-3"></a>

### Q7.3 Agent 通信与并发改代码如何设计？

**口述答案：**通信可以用队列、共享状态、直接调用或事件总线，但关键是协议语义：版本、状态、结果引用、错误与超时。模型自然语言只是解释字段，不承担唯一状态真相。

并行任务先分配不重叠写范围、独立工作区和明确依赖；集成时检查基线版本、接口变更、冲突和回归。对同一个文件或同一数据库对象，使用单写者、队列化或乐观版本校验。

**取舍：**集中调度容易审计，可能形成瓶颈；分布式协作扩展性更好，但更难处理因果、去重和故障。自动合并文本冲突不等于业务语义无冲突。[S10](05_参考来源与版本说明.md#s10)[S11](05_参考来源与版本说明.md#s11)

## 8. RAG 与知识库

对应原题：P001「知识库怎么做」；P004「维护」；P015「召回优化」；P017「优化准确性」；P018「检索」。

<a id="q8-1"></a>

### Q8.1 从文档到可用 RAG 的完整流程是什么？

**口述答案：**采集和解析时保留结构与来源，清洗去噪后按语义分块，附版本、时间、权限和层级元数据，建立关键词/向量索引，检索重排后将可追溯证据提供给模型。

PDF/表格/代码分块方式不同；表格要保留表头，代码要尽量保留函数与调用上下文。检索前确定租户与允许文档范围，返回证据时再次校验。新文档、更新、删除和权限撤回都要同步到索引与缓存。

**非目标：**不是“把 Markdown 全存向量库”就完成；还需要质量评测、增量更新、故障降级和运营维护。[S12](05_参考来源与版本说明.md#s12)[S05](05_参考来源与版本说明.md#s05)

<a id="q8-2"></a>

### Q8.2 关键词、向量、混合检索与 rerank 怎么选择？

**口述答案：**关键词适合精确标识和术语，向量适合语义近似，多路融合兼顾两者；rerank 对候选重新估计相关性。是否更好，要用本业务测试集验证。

BM25 分数和向量相似度未必同尺度，不能未经标定直接用固定 `0.6/0.4` 相加作为通用最优方案。可以用 RRF 等排名融合，或校准后加权，再做重排；Azure AI Search 文档给出混合检索并行召回与 RRF 的实现示例。

先确认解析、chunk、权限过滤和查询改写质量，再调 embedding、候选数与 rerank。召回不到的材料，重排无法补出来；召回太多也会增加噪声、成本和上下文压力。[S12](05_参考来源与版本说明.md#s12)

<a id="q8-3"></a>

### Q8.3 RAG 准确性怎么评测？Recall@K 与 Precision@K 有何区别？

**口述答案：**检索与生成分层评测，端到端再确认任务价值。不能只看答案流畅或向量相似度。

- `Precision@K = Top-K中相关项数 / 实际评价的K个位置数`。
- `Recall@K = Top-K中相关项数 / 该查询全部相关项数`。
- MRR 看第一个相关结果的位置；NDCG 综合相关性等级和排序。
- 生成测回答正确性、对证据的忠实度、引用正确性和拒答质量，配合人工评审校准。

相关项真值集合难穷尽时，要交代标注范围，别把估计召回率当真实全集召回率。将失败拆为无资料、解析错误、检索漏召、重排错误、版本过期、生成未忠实使用证据。[S01](05_参考来源与版本说明.md#s01)[S12](05_参考来源与版本说明.md#s12)上述基础指标公式在文中直接定义，防止同名指标混用。

<a id="q8-4"></a>

### Q8.4 小知识库用文件还是 RAG？怎样维护频繁更新？

**口述答案：**规模小、结构稳定、可直接定位时，读取文件或精确查询可能更简单；文档多、语义入口多且内容持续变化时，检索系统更有价值。不是所有问题都必须 RAG。

维护采用文档 ID、版本、内容哈希、增量索引和删除台账，区分索引建好与切换完成。检索结果附版本和有效时间，缓存键包含知识/权限版本；旧结果不能继续向已撤销权限的用户提供。

业务规则和高风险动作不能仅作为可选检索证据：强制约束由服务端执行，文档帮助理解。微调与 RAG 也不是二选一；前者偏行为/能力适配，后者提供可更新证据。[S12](05_参考来源与版本说明.md#s12)[S05](05_参考来源与版本说明.md#s05)

## 9. 权限、安全与沙箱

对应原题：P006「小龙虾安全」；P011「AI 沙箱」；P018「Agent 权限」「查询隔离」。P015 的事务隔离级别请参见 Q14，不要把数据库隔离等级等同于 Agent 授权隔离。

<a id="q9-1"></a>

### Q9.1 Agent 如何控制权限与防 Prompt Injection？

**口述答案：**按真实用户/租户授权，为每次工具调用做服务端校验；外部网页、文件和工具输出都是数据，不能自行变成更高权限指令。

采用最小权限、短期凭证、资源 allowlist、参数校验、敏感操作审批和完整审计。密钥留在受控执行端，不拼进 Prompt。搜索、读取、修改、发布分别授权，用户有读权限不代表 Agent 有执行权限。

Prompt Injection 不能只靠“忽略恶意指令”。需要限制可执行能力、网络出口和数据流，识别输出中的指令诱导，独立检查敏感动作；模型检测只能作为补充。不能让工具结果里的“用户已授权”替代真实授权记录。[S05](05_参考来源与版本说明.md#s05)[S13](05_参考来源与版本说明.md#s13)

<a id="q9-2"></a>

### Q9.2 AI 沙箱怎么实现？容器等于安全沙箱吗？

**口述答案：**沙箱是权限与资源边界，不只是一个临时目录。限制文件系统、网络、进程、CPU、内存、时长与可用凭证，并明确生命周期和清理策略。

工作区只挂必要文件，默认非特权身份，限制 host 挂载与运行时管理接口，网络按目标放行。对不可信代码根据风险选择更强隔离，如额外内核隔离或独立虚拟化执行环境；单个普通容器不是绝对安全边界。

区分用户状态与执行状态：持久产物经校验后导出，临时环境用完销毁；常驻池提升启动速度但增加串租户、残留凭证与资源泄漏风险。是否采用预热池需要压测和安全验证。[S05](05_参考来源与版本说明.md#s05)[S15](05_参考来源与版本说明.md#s15)此处是分层防御建议，不代表 Kubernetes 直接保证不可信代码安全。

<a id="q9-3"></a>

### Q9.3 Agent 访问 URL 如何防 SSRF？

**口述答案：**控制请求实际到达的位置，而不只是检查 URL 文本。限定协议和可信域，解析并校验目的地址，处理重定向、IPv4/IPv6、DNS 变更和编码绕过。

阻断非授权内网、loopback、链路本地及云元数据地址；每次重定向重新校验，出口代理或网络策略再加一道限制。不要把“用户要求抓网页”解释为允许访问任意内网资源，也不要默认所有 URL 都能请求。

**取舍：**严格 allowlist 最易治理，但影响开放搜索；开放场景需要更强网络隔离和审计。字符串正则匹配域名不是充分防护。[S13](05_参考来源与版本说明.md#s13)

## 10. Docker、Kubernetes 与部署

对应原题：P003「Java 容器化」「从零搭建 k8s」；P009「Deployment 和 StatefulSet」；P011「算法工程部署」「多个 Pod 共享硬盘」。

<a id="q10-1"></a>

### Q10.1 Java/模型服务怎样容器化并上线？

**口述答案：**先把运行依赖、启动入口和配置明确成可复现镜像，再定义资源、健康检查、发布与回滚。容器化不等于把宿主机目录打包复制进去。

构建固定依赖和镜像版本，运行身份最小权限，配置与密钥外置。为服务设置 requests/limits、启动/就绪/存活探针，考虑优雅退出、日志与指标。JVM 评估容器内存与堆外开销；模型服务还要测权重加载、GPU/驱动兼容、批处理、并发和冷启动。

从零搭平台还涉及控制平面、节点、网络、DNS、存储、RBAC、镜像供应链、备份和运维；不要在不了解生产要求时给“一条命令就够”的承诺。[S14](05_参考来源与版本说明.md#s14)[S16](05_参考来源与版本说明.md#s16)

<a id="q10-2"></a>

### Q10.2 Deployment 与 StatefulSet 区别？怎样无感更新？

**口述答案：**Deployment 适合可替换副本的服务；StatefulSet 提供稳定的副本标识与存储关联等语义，适合需要这些特性的工作负载。StatefulSet 不会自动替业务实现一致性。

更新需要 readiness、容量余量、流量切换与退出排空，结合 maxSurge/maxUnavailable 等策略。终止时让在途请求、流式连接和后台任务有结束或迁移机制，旧/新版本接口及数据库迁移保持兼容。

**常见错误：**“滚动更新自动零停机”。依赖单点、启动慢、长连接和破坏性 schema 变更都可能造成中断；数据库迁移常需 expand/contract，而不是直接删除旧字段。[S14](05_参考来源与版本说明.md#s14)[S16](05_参考来源与版本说明.md#s16)

<a id="q10-3"></a>

### Q10.3 多 Pod 挂同一卷会不会冲突？RWO 能不能当互斥锁？

**口述答案：**要分清存储访问模式与业务并发语义。ReadWriteOnce 通常限制到一个节点，不一定只有一个 Pod；同节点多个 Pod 仍可能访问。ReadWriteOncePod 是另一种模式，也受驱动支持等条件限制。

允许共享挂载不代表文件/数据库操作自动线程或进程安全。应根据存储和应用语义采用单写者、文件锁、数据库事务、队列或独立卷。网络文件系统的锁和缓存语义还要核实实际实现。

**原题 NFS 与 VPC：**它们分别属于网络文件系统和网络隔离/组织概念，不是同层替代方案。应先澄清问题意图，不能编造一张“谁性能更好”的对比表。[S15](05_参考来源与版本说明.md#s15)

## 11. Go 调度、GC 与并发

<a id="q11-1"></a>

### Q11.1 GMP 模型是什么，协程切换做了什么？

原题定位：P005「GMP模型」「go协程切换做了什么事，并发量如何控制」；P010「Go 协程调度」。

**核心答案：**G 是 goroutine，M 是操作系统线程，P 是执行 Go 代码所需的调度资源。M 通常需要持有 P 才能执行用户 Go 代码；调度器结合本地运行队列、全局队列、网络轮询和工作窃取安排 G。协程切换保存、恢复执行上下文，换到另一条 G 的栈继续运行，不等于每次都切换操作系统线程。阻塞系统调用时可释放 P，让其他 M 接手。[B01](05_参考来源与版本说明.md#b01)

**边界与取舍：**`GOMAXPROCS` 主要限制同时执行 Go 代码的线程数，不限制全部 M 或 G 的数量。Go 1.14 引入异步抢占；Go 1.25 的默认值开始考虑容器 CPU 限额等因素，应结合实际版本和部署配置回答，不能背固定的调度队列细节当语言规范。[B02](05_参考来源与版本说明.md#b02)[B03](05_参考来源与版本说明.md#b03)

<a id="q11-2"></a>

### Q11.2 如何控制并发，context 能强制终止 goroutine 吗？

原题定位：P005「go协程切换做了什么事，并发量如何控制」；P019「Go的context底层原理」。

**核心答案：**并发控制应同时限制在途任务、排队长度和下游资源，常用固定 worker、有界队列或信号量。`context` 是取消、截止时间和值的传播机制；可取消 context 维护取消状态及子节点，取消时通知 `Done`，并向子节点传播。它不是“杀协程”接口，业务必须主动监听取消，或调用支持 context 的 I/O API。[B04](05_参考来源与版本说明.md#b04)

**建议：**先按数据库连接数、外部接口配额和任务耗时估算上限，再压测调整；满载时明确等待、拒绝或降级。创建可取消 context 后及时调用 cancel，并保证所有退出路径释放令牌、关闭资源。常见错误是先无限启动 G 再让其排队，或以为超时返回后后台副作用自动停止；共享内存仍须符合 Go 内存模型。[B04](05_参考来源与版本说明.md#b04)[B05](05_参考来源与版本说明.md#b05)

<a id="q11-3"></a>

### Q11.3 slice 与 Python list 类似在哪里，为什么数据会被覆盖？

原题定位：P004「go 的 slice 和 python 的什么数据结构类似，区别是啥？，有没有遇到过数据非预期被覆盖的情况？」。

**核心答案：**二者都能表示可变长度序列，但不能等同实现。Go slice 是对底层数组的视图，包含指针、长度、容量；多个切片可能共享数组。容量够时 `append` 可以复用原数组，改元素会影响其他视图；容量不足时才分配新的数组。Python list 存放对象引用，赋值会形成同一个列表的别名，而列表切片创建新的列表容器，元素对象仍可能共享。[B06](05_参考来源与版本说明.md#b06)[B07](05_参考来源与版本说明.md#b07)

**建议：**需要独立所有权时显式复制；传递给异步任务前确认生命周期和是否共享。Go 全切片表达式限制容量可以迫使后续扩容，但不会隔离已有元素写入；`copy` 和 Python 浅拷贝也不会递归复制指针指向的对象。面试应解释可复现的共享机制，不编造“自己在线上踩过坑”。[B06](05_参考来源与版本说明.md#b06)[B07](05_参考来源与版本说明.md#b07)

<a id="q11-4"></a>

### Q11.4 Go GC 怎么工作，如何判断 GC 是否造成性能问题？

定位：主题 11 的 GC 复习扩展；索引展示的五条原题没有单独列出 GC 问题，不认定为某个 P 的原问。

**核心答案：**Go GC 以并发追踪为基础，标记可达对象并回收不可达内存；它仍有 STW 阶段，不能说“完全不停顿”。并发标记、写屏障以及必要的 mutator assist 都会消耗 CPU。`GOGC` 调节堆增长目标，`GOMEMLIMIT` 提供软内存限制；提高前者通常以更多内存换取较低 GC 频率，软限制也不是严格的进程 RSS 上限。[B08](05_参考来源与版本说明.md#b08)

**建议：**先看分配速率、存活堆、GC CPU、暂停分布及请求尾延迟，再用 pprof 定位短命对象和长期引用，优先减少无谓分配。不要看到一次 GC 就归因，也不要未经测量大量引入对象池。Go 1.25 的 Green Tea 为实验性实现；回答其他版本时核对实际启用状态，不把单一版本内部算法推广为永久事实。[B03](05_参考来源与版本说明.md#b03)[B08](05_参考来源与版本说明.md#b08)

## 12. 高可用、限流与稳定性

对应原题：P005「服务爆量」；P007「告警/日志/故障定位」「运维指标」；P011「高可用」「单点依赖」。

<a id="q12-1"></a>

### Q12.1 服务爆量怎么保证可用？

**口述答案：**先定义 SLO 与容量，再在入口和执行层控制流量、并发及队列，让系统在过载时有界降级而非无限堆积。

措施包括分租户配额、令牌桶/并发上限、有限队列、deadline、熔断、优先级降级和负载分担。异步化适合可延后任务，但只是把拥塞转移到队列，不能无限缓存。扩容需要考虑冷启动和下游容量。

**Agent 特别注意：**一条用户请求可能触发多次模型/工具调用，要分别限制请求数、任务并发和 Token 预算。只限 HTTP QPS 不能保护实际成本和执行资源。[S17](05_参考来源与版本说明.md#s17)

<a id="q12-2"></a>

### Q12.2 超时、重试、降级怎样配合？

**口述答案：**先传递剩余 deadline，再对可恢复、可安全重试的错误做有预算的重试，带指数退避和 jitter；持续故障时熔断并降级。

只在选定层重试，避免上下游每层都重试造成倍增。超时不代表没有执行，支付、发信、发布等操作必须有幂等或查询确认。客户端取消还要传到任务与工具端，防止用户退出后工作继续消耗资源。

降级应说明能力损失：只读、旧数据、排队或转人工，不伪造“完成”。重试次数、超时和失败率阈值来自压测与错误预算，不是固定“重试三次最正确”。[S17](05_参考来源与版本说明.md#s17)

<a id="q12-3"></a>

### Q12.3 单点依赖与故障定位怎么处理？告警越少越好吗？

**口述答案：**找清关键依赖，区分可恢复故障、不可用依赖和共享状态。多副本、选主、备份和容灾要与恢复目标匹配；不能只把服务多开两份就宣称消除了单点。

定位结合 metrics、logs、traces：先看影响范围与近期变更，再沿请求链路查耗时、错误、资源饱和、依赖和队列。告警围绕用户影响及 SLO，做关联聚合和可执行指引，但避免压掉真正事故。

衡量有效告警比例、漏报、发现时间和 MTTR。日志和轨迹要脱敏，控制基数与采样，不能为了“全量可观测”记录所有密钥、用户原文和大对象。[S17](05_参考来源与版本说明.md#s17)[S18](05_参考来源与版本说明.md#s18)

## 13. 网络、HTTP 与 RPC

对应原题：P003「网络不通」「网络工具」；P009「tRPC/gRPC」；P018「正反向代理」「nginx 路由」。

<a id="q13-1"></a>

### Q13.1 网页打不开、网络不通，怎么分层排查？

**口述答案：**先固定现象与范围，再沿客户端、DNS、网络路径、TLS、代理、后端和依赖逐层检查，不一上来重启全部服务。

确认是单用户、单域名、单区域还是全部失败；区分连接失败、证书问题、HTTP 错误、超时和前端渲染错误。检查解析结果、目标端口、路由与策略、握手和代理访问日志，再关联服务端 trace。

在授权环境用 `curl -v`、DNS 查询工具、`ss`/`netstat`、抓包和服务日志取证。ICMP ping 通不能证明 TCP 端口、TLS、HTTP 或业务正常；ping 不通也不直接证明目标服务不可达。[S19](05_参考来源与版本说明.md#s19)[S18](05_参考来源与版本说明.md#s18)工具次序依环境调整。

<a id="q13-2"></a>

### Q13.2 正向代理、反向代理和 Nginx 路由怎么理解？

**口述答案：**正向代理代客户端访问目标，反向代理作为服务入口把请求转给后端；Nginx 常用于反向代理、TLS 终止、路由和负载分担，但配置决定实际行为。

路由可以按 host、path 等规则，注意路径改写、匹配优先级、上游超时和原始请求信息传递。信任代理头必须限定可信代理来源，否则客户端可伪造源 IP 等信息。

网关不自动提供端到端授权；后端仍校验租户与资源权限。长连接与流式返回还需要检查缓冲、超时和连接排空。[S19](05_参考来源与版本说明.md#s19)[S21](05_参考来源与版本说明.md#s21)

<a id="q13-3"></a>

### Q13.3 HTTP 与 RPC、gRPC 与 tRPC 怎么比较？

**口述答案：**HTTP 是协议语义，RPC 是调用抽象，二者不互斥。gRPC 定义服务调用、流式通信、状态、deadline 等机制；应用仍要处理超时和副作用。

选择时比较接口 schema、编码、互操作、浏览器支持、流式需求、服务发现、负载均衡和内部治理。常见 gRPC 使用 Protobuf，但不要把某种序列化或传输组合当作所有 RPC 的定义。

**tRPC：**先确认指腾讯 tRPC 还是 TypeScript 生态同名项目，再限定使用的语言和版本。腾讯服务治理能力、插件和内部平台集成需要根据实际框架核实；不应简单回答“tRPC 就是加了某个功能的 gRPC”。[S20](05_参考来源与版本说明.md#s20)[S19](05_参考来源与版本说明.md#s19)

<a id="q13-4"></a>

### Q13.4 大模型流式输出一定用 SSE，不能用 WebSocket 吗？

**口述答案：**不是。单向服务器推送且希望复用 HTTP 时，SSE 往往简单；需要频繁双向通信、实时音频或交互控制时，可考虑 WebSocket。后端流式调用还可能使用其他传输方案。

SSE 用事件分帧，不等于一次网络 read 就是一条事件。JSON 增量必须按协议边界累积解析，不能直接对任意半段做完整 JSON parse。客户端断开要取消上游，考虑反压、心跳、重连和事件去重。

浏览器原生 EventSource 对方法/自定义请求头的限制与 fetch 流式读取不同；鉴权和重连策略按实现选择。代理缓冲可能让后端有流但前端看不到。[S21](05_参考来源与版本说明.md#s21)[S19](05_参考来源与版本说明.md#s19)

## 14. 数据库与 SQL 优化

<a id="q14-1"></a>

### Q14.1 慢 SQL 怎么查，重点看哪些字段？

原题定位：P005「sql优化有什么思路」；P024「sql慢查询需要关注什么字段」。

**核心答案：**先区分执行慢、锁等待、连接排队和结果传输慢，再选择优化手段。慢日志里的 `Query_time`、`Lock_time`、`Rows_sent`、`Rows_examined` 有助于识别耗时和扫描放大；还要结合调用频次和总资源消耗，而不是只找最慢的一次。记录实际参数、数据规模和分布，避免脱离现场分析。[B09](05_参考来源与版本说明.md#b09)

**建议：**看 `EXPLAIN` 的访问方式、候选及实际索引、估算行数和过滤比例；再用支持版本的 `EXPLAIN ANALYZE` 对比实际执行。后者会执行语句，不能随意在生产跑重查询。依次减少读取数据、改写查询、设计索引，最后考虑分区或拆分。常见错误是把 `Using filesort` 当作一定落盘，或只凭“用了索引”判断已经快。[B10](05_参考来源与版本说明.md#b10)

<a id="q14-2"></a>

### Q14.2 联合索引怎么设计，为什么索引不一定有效？

定位：P005「sql优化有什么思路」的索引设计扩展，不宣称原帖单独问过联合索引。

**核心答案：**B-tree 联合索引通常按最左前缀组织可用查找范围，要结合过滤、排序、分组和覆盖需求设计，不是把所有 WHERE 字段塞进去。等值条件与范围条件的组合影响可构造的连续范围；范围条件之后的列仍可能用于索引条件过滤或覆盖，不能笼统说“后面全部失效”。优化器也可能因成本估算选择全表扫描。[B11](05_参考来源与版本说明.md#b11)[B12](05_参考来源与版本说明.md#b12)

**建议：**根据高频查询形态比较候选索引，并用实际计划、扫描行数、写入成本验证。覆盖索引减少回表，但会扩大索引和写放大；深分页可考虑以稳定排序键做游标分页。函数包装、隐式类型转换是否影响索引要看表达式、类型和版本，避免“只要有函数就绝不走索引”这类绝对化回答。[B10](05_参考来源与版本说明.md#b10)[B11](05_参考来源与版本说明.md#b11)[B12](05_参考来源与版本说明.md#b12)

<a id="q14-3"></a>

### Q14.3 MySQL 默认隔离级别是什么，可重复读能解决什么？

原题定位：P015「mysql事务隔离级别」。

**核心答案：**MySQL 8.4 的 InnoDB 默认隔离级别是可重复读，但实例和会话可以改配置，其他存储引擎也不能直接套用。可重复读下，普通一致性读通常使用事务首次一致性读建立的快照；读已提交则每次一致性读获得新快照。普通快照读与 `SELECT ... FOR UPDATE`、UPDATE 等锁定或修改行为不能混为一谈。[B13](05_参考来源与版本说明.md#b13)[B14](05_参考来源与版本说明.md#b14)

**工程边界：**MVCC 不等于整个事务看到一个永远不变的世界：事务可看到自身修改，混用快照读和锁定操作有不同可见性。InnoDB 的范围锁定读可借助 next-key locking 防止相应范围的幻行插入，但不能据此宣称可重复读就是完全串行化。库存扣减等约束宜用条件更新、锁或唯一约束，并处理死锁重试。[B13](05_参考来源与版本说明.md#b13)[B14](05_参考来源与版本说明.md#b14)

<a id="q14-4"></a>

### Q14.4 Hive 大表查询很慢，和 MySQL 优化思路有什么不同？

原题定位：P021「查 Hive 表，数据量很大、查询很慢怎么优化」。

**核心答案：**Hive 的典型瓶颈是扫描量、分布式计算、数据倾斜和 shuffle，不宜照搬 OLTP 的“加 B-tree 索引”。先看 EXPLAIN 和任务指标，检查分区裁剪、谓词下推、列裁剪、统计信息与 JOIN 策略；确认过滤条件是否真正降低读取量，而不是只在结果阶段过滤。[B15](05_参考来源与版本说明.md#b15)

**建议：**按查询模式选择分区和适合的列式格式；小表广播 JOIN 须验证内存预算，大表 JOIN 需观察热点 key 与任务耗时分布。减少小文件、先聚合再关联可以降低开销，但预聚合要保持统计口径；去重、NULL 与外连接语义不能为了“提速”改坏。具体执行引擎和版本未给出，因此不承诺某个配置必然有效，也不编造性能提升百分比。[B15](05_参考来源与版本说明.md#b15)

## 15. 前端框架与浏览器

<a id="q15-1"></a>

### Q15.1 Vue 与 React 响应式和渲染有什么区别？

**口述答案：**两者都把状态变化映射到 UI，但跟踪变化和组织渲染的方式不同。Vue 的响应式依赖跟踪与 React 的状态更新/重新渲染思路不能简单混为“双向绑定”。

Vue 相关机制会按响应式依赖触发更新；React 常通过 state 更新触发重新渲染，props 及单向数据流组织组件。Vue 的 v-model 也是特定输入/更新约定，React 可用受控组件实现输入状态同步。

**追问重点：**状态放在哪、列表 key 稳定性、异步请求竞态、生命周期/副作用、组件边界和不必要渲染。两者性能没有不看场景的绝对排名，具体机制随版本核实。[S22](05_参考来源与版本说明.md#s22)[S23](05_参考来源与版本说明.md#s23)

<a id="q15-2"></a>

### Q15.2 前后端怎样协作，让 Agent 减少联调成本？

**口述答案：**先定义接口、字段、错误、鉴权、分页/排序和状态转换，再用 schema/类型与契约测试保证一致。Agent 帮助生成适配和测试，但不能自行决定双方未确认的业务含义。

接口版本、样例、mock 与测试基线同步维护；处理幂等提交、重复点击、取消、超时和异步任务状态。前端不要把“按钮变灰”当权限控制，后端也不能把格式正确等同于业务合法。

**收益验证：**统计接口变更后的返工与联调时间，而不是仅看生成页面数量。这是基于接口契约与质量验证的工程建议。[S02](05_参考来源与版本说明.md#s02)[S19](05_参考来源与版本说明.md#s19)

<a id="q15-3"></a>

### Q15.3 怎样验证 AI 生成的页面符合预期？

**口述答案：**把预期拆成可执行用户行为、数据状态和视觉/可访问性要求。组件测试、端到端流程和独立人工检查组合使用，不只看截图“像不像”。

**独立性：**业务负责人或可信基线维护验收场景，开发 Agent 不能为通过测试任意改基线。LLM 看图可补充，但不能替代真实请求结果、DOM 行为和权限验证。[S02](05_参考来源与版本说明.md#s02)[S22](05_参考来源与版本说明.md#s22)[S23](05_参考来源与版本说明.md#s23)

## 16. Redis、缓存与分布式锁

<a id="q16-1"></a>

### Q16.1 Redis 锁怎么加、怎么安全释放，TTL 为什么还不够？

原题定位：P005「redis分布式锁」；P008「Red set nx 错误释放所有什么场景」。后者为含混简写，此处仅提供相关锁知识，不替原文补写确定含义。

**核心答案：**单实例基础锁可用 `SET key 随机令牌 NX PX ttl` 原子获取；释放应在一个原子操作中比对令牌后删除，避免删掉后继持有者的锁。分开执行 SETNX、设置过期时间，或无条件 DEL，都存在故障窗口。主从异步复制下故障切换也可能破坏互斥，必须明确部署与故障模型。[B16](05_参考来源与版本说明.md#b16)

**关键边界：**旧持有者可能暂停到 TTL 过期，新持有者已获取锁，而旧持有者恢复后仍写外部系统。令牌比对释放只能防误删，续租也不能彻底消除这种副作用。严格保护需由受保护资源校验单调递增的 fencing token 并拒绝旧 token；随机锁令牌不是 fencing token。资源不支持时应另选数据库约束等方案。Kubernetes RWO 只是单节点读写挂载语义，同节点多个 Pod 仍可访问，不是应用互斥。[B16](05_参考来源与版本说明.md#b16)[B17](05_参考来源与版本说明.md#b17)

<a id="q16-2"></a>

### Q16.2 RDB 与 AOF 有什么区别，如何选择持久化？

原题定位：P005「redis持久化方案」。

**核心答案：**RDB 保存时间点快照，通常紧凑、适合备份和恢复，但可能丢失最近一次快照后的数据；AOF 记录写操作，持久性取决于刷盘策略。`appendfsync everysec` 通常以秒级数据损失窗口换吞吐，`always` 更重，也不能脱离操作系统和存储故障模型承诺绝对零丢失。Redis 7 起采用多文件 AOF，不能把所有版本都解释为一个无限增长的文件。[B18](05_参考来源与版本说明.md#b18)

**建议：**先确认 Redis 是可重建缓存还是承载不可轻易丢失的业务状态，再定 RPO、RTO、备份和恢复演练。fork、写时复制及重写可能影响内存和延迟，需保留余量。复制不等于备份，副本也可能同步误删除；启用 AOF 更不等于可以替代订单等核心系统的数据库事务。[B18](05_参考来源与版本说明.md#b18)

<a id="q16-3"></a>

### Q16.3 Redis 是单线程的吗，为什么慢命令会影响请求？

原题定位：P010「Redis 线程模型是怎样的」。

**核心答案：**“Redis 单线程”主要概括常见命令核心执行路径，不是整个进程只有一个线程。网络 I/O、后台任务和持久化可能使用线程或子进程；Redis 8 的 I/O threading 进一步改进了网络处理，但 I/O 并行不意味着所有命令都任意并行执行。回答应明确版本、配置和是否使用模块。[B18](05_参考来源与版本说明.md#b18)[B19](05_参考来源与版本说明.md#b19)

**建议：**排查大 key、长 Lua、重命令、网络排队和持久化抖动；分别看命令延迟及主机指标。限制一次处理规模，批处理也要有边界，不能因为用了 pipeline 就无限堆请求。常见错误是认为单线程就没有任何并发故障：多客户端之间跨命令的读改写仍可交错，需要原子命令、事务或脚本保护，而原子执行也不等于故障后一定持久。[B16](05_参考来源与版本说明.md#b16)[B18](05_参考来源与版本说明.md#b18)[B19](05_参考来源与版本说明.md#b19)

<a id="q16-4"></a>

### Q16.4 zset 按什么排序，可以怎样服务排行榜与缓存？

原题定位：P018「Redis zset讲下 排序依据」；缓存策略为该主题复习扩展。

**核心答案：**zset 成员唯一，以 score 排序；score 相同按成员的字节字典序决定次序，不是插入先后或中文拼音顺序。重复添加同一成员通常更新其分数；分数相同的排名若要满足业务规则，应显式编码次序或在上层处理，不能假设天然稳定于事件发生时间。[B20](05_参考来源与版本说明.md#b20)

**建议：**排行榜要限定范围查询、保留规模及更新规则，避免一次返回所有成员。把 zset 或普通键作为数据库数据的缓存时，先确定可接受陈旧时间，使用有界 TTL、热点重建合并和故障降级；这些是工程策略，不是 Redis 自带的数据库一致性协议。常见错误是用浮点 score 拼接超大时间戳导致精度风险，或把每次缓存写成功当作数据库事务已提交。[B20](05_参考来源与版本说明.md#b20)[B21](05_参考来源与版本说明.md#b21)

## 17. DDD、事件驱动与架构设计

<a id="q17-1"></a>

### Q17.1 DDD 解决什么问题，怎样开始建模？

原题定位：P003「详细介绍DDD，有什么建模方法，详细说下聚合根的作用」；P005「DDD架构」；P018「为什么要用 DDD？它解决了什么问题？」。

**核心答案：**DDD 面向业务复杂性，用统一语言、限界上下文和领域模型避免同一概念在不同业务中混用。战略设计先划定领域边界，战术设计再考虑实体、值对象、聚合和领域服务；不应先根据数据库表画一套“领域对象”，再强行解释业务。DDD 也不是某个框架或必须采用微服务。[B22](05_参考来源与版本说明.md#b22)

**建议：**从业务流程、命令、事件和不变量入手，与业务人员验证边界，再把模型映射到代码。领域层表达规则，应用层编排用例，基础设施实现持久化和消息等依赖。复杂业务值得这种成本；简单 CRUD 可以采用更轻结构。常见错误是堆满 Repository、Service 类就称为 DDD，实际规则仍散落在控制器和 SQL 中。[B22](05_参考来源与版本说明.md#b22)

<a id="q17-2"></a>

### Q17.2 订单域如何拆实体、值对象和聚合根？

原题定位：P018「订单域里，实体和子对象你怎么拆？」；P003「聚合根的作用」。

**核心答案：**实体强调身份，值对象强调值相等；聚合是一组需共同维护不变量的对象，聚合根是外部修改的入口。假设订单金额、明细与订单状态必须一起满足规则，可把订单作为根，在受控方法中校验，而不是让外部任意修改明细。是否属于同一聚合由业务一致性边界决定，不由 ORM 外键或级联关系决定。[B23](05_参考来源与版本说明.md#b23)

**取舍：**不要把用户、库存、支付全部塞进订单聚合；聚合过大会放大锁竞争和加载成本。跨聚合通常通过标识引用，并用事件协调，但业务要求强一致时仍应重新评估边界和事务方案。“只能经聚合根修改”是领域设计约束，不是数据库自动提供的访问限制，仍需封装、并发控制及持久化实现支撑。[B23](05_参考来源与版本说明.md#b23)

<a id="q17-3"></a>

### Q17.3 领域事件和集成事件有什么区别，何时发布？

原题定位：P003「事件驱动」。

**核心答案：**领域事件表达领域内已发生的事实，用于显式触发规则和解耦；集成事件面向其他上下文或服务，通常描述已提交、可对外观察的变化。二者可以转换，但不宜把内部实体结构直接暴露为长期消息契约。领域事件在事务前处理还是提交后处理，会改变一致性和失败语义，必须明示。[B24](05_参考来源与版本说明.md#b24)

**建议：**对外发布可用 outbox：业务修改和待发事件在同一本地事务提交，再由独立进程投递。消费者应处理重复、乱序和契约演进；消息字段包含事件 ID、业务 ID 与必要版本。常见错误是先提交数据库再直接发消息，漏掉两者之间崩溃造成的丢事件；反过来先发消息也可能暴露最终回滚的状态。[B24](05_参考来源与版本说明.md#b24)[B21](05_参考来源与版本说明.md#b21)

<a id="q17-4"></a>

### Q17.4 AI 为通过测试改坏领域规则，怎样防止？

原题定位：P004「DDD AI 为了通过单元测试，改了代码，怎么避免」。

**核心答案：**测试通过只是证据之一，不能定义业务真相。先把经确认的不变量、状态迁移和跨边界契约写清楚，让实现与测试都接受这些约束；关键规则由领域模型执行，不能靠某个测试桩暗中保证。AI 的修改还需人工检查是否绕开聚合根、删除校验或把失败场景改成成功。[B23](05_参考来源与版本说明.md#b23)

**建议：**补充非法迁移、并发更新、边界金额等反例测试，并检查数据库约束和事件契约；生成测试与修改生产代码分开审阅。必要时用性质测试或变异测试评估约束覆盖。这里是基于领域不变量的工程建议，不是 Microsoft 文档宣称某种 AI 流程有固定效果。常见错误是为了绿灯删除断言、重写预期，或用 mock 掩盖真实事务边界。

## 18. Python 与 GIL

<a id="q18-1"></a>

### Q18.1 GIL 是什么，I/O 阻塞会一直占用它吗？

原题定位：P008「Python如果多线程里面IO阻塞，会影响gil锁吗」。

**核心答案：**传统带 GIL 的 CPython 中，同一时刻通常只有一个线程执行 Python 字节码，这不是所有 Python 实现的语言级规定。常见阻塞 I/O 会释放 GIL，让别的线程运行；某些 C 扩展也可在计算时释放它。纯 Python CPU 密集任务通常不能靠这种多线程获得多核并行，但不能反推“Python 线程没有任何用途”。[B25](05_参考来源与版本说明.md#b25)[B26](05_参考来源与版本说明.md#b26)

**版本边界：**CPython 3.13 起有可选 free-threaded 构建，3.14 文档单独说明它的行为；它不等于普通构建默认没有 GIL。不兼容的扩展还可能重新启用 GIL，应核对构建、运行状态与扩展兼容性。无 GIL 也不代表复合业务操作自动线程安全，容器内部保护不能替代应用锁。[B27](05_参考来源与版本说明.md#b27)

<a id="q18-2"></a>

### Q18.2 多线程、多进程、asyncio 怎样选，线程池有何风险？

原题定位：P008「Python实现串行和并行有什么区别，多进程和多线程的区别」；P018「Python 多线程是怎么实现的？线程池呢？」。

**核心答案：**并发是多个任务交替推进，并行是同时执行。传统 CPython 的 I/O 密集任务可选线程池或 asyncio；CPU 密集的纯 Python 任务常选进程池，但需付出序列化、进程启动与内存成本。asyncio 依靠协作调度，并不会把普通阻塞调用自动变成非阻塞；C 扩展释放 GIL 或 free-threaded 构建时要重新评估线程方案。[B25](05_参考来源与版本说明.md#b25)[B27](05_参考来源与版本说明.md#b27)[B28](05_参考来源与版本说明.md#b28)

**建议：**限制 worker 和提交量，设置超时、取消与异常处理，避免池内任务同步等待同池中尚未运行的任务造成死锁。不要依赖跨版本固定的默认 worker 数。Python 3.14 的进程池默认启动方式已不再默认使用 fork，初始化成本和可序列化要求需按平台实测；进程隔离也不自动解决外部数据库并发。[B28](05_参考来源与版本说明.md#b28)

<a id="q18-3"></a>

### Q18.3 with 包裹对象是什么机制，会吞异常吗？

原题定位：P008「Python with包裹class有什么特点」。原文未明确是类对象、实例还是特定封装，以下按上下文管理协议解释，不据此认定原帖意图。

**核心答案：**普通 `with` 使用上下文管理器，进入时调用 `__enter__`，返回值可绑定给 `as`；成功进入后，退出时调用 `__exit__`，把异常信息传给它。若 `__exit__` 返回真值，异常被抑制，否则继续传播。通常使用实现协议的实例，而不是“任何 class 都能直接包起来”。[B29](05_参考来源与版本说明.md#b29)

**建议：**用于文件、锁、连接等资源的确定性释放。若 `__enter__` 本身失败，需要在进入过程中处理已申请资源，不能期待对应 `__exit__` 自动补救；异步资源用 `async with` 和异步协议。常见错误是无条件返回 True 吞掉业务异常，或把 with 当成数据库事务已经提交的保证，实际提交和回滚仍取决于具体管理器实现。[B29](05_参考来源与版本说明.md#b29)

<a id="q18-4"></a>

### Q18.4 列表切片与赋值有哪些别名问题，GIL 能保护读改写吗？

原题定位：P004 的 Go slice 与 Python 数据结构比较；读改写为该主题并发扩展。

**核心答案：**`b = a` 绑定同一个列表；`b = a[:]` 建立新的外层列表，但可变元素仍共享，所以修改嵌套对象可能影响两者。深拷贝适用于需要递归复制的场景，但复制范围、不可复制资源和成本都需评估，不能把“复制一切”当作默认设计。[B07](05_参考来源与版本说明.md#b07)

**建议：**明确数据所有权，能用不可变值或消息传递就减少共享；必须共享时把整个业务不变量放在同步边界内。传统 GIL 也不能保证“检查再写入”等多步骤逻辑原子化，free-threaded 下更不应依赖偶然的内建行为。常见错误是把引用传递说成值拷贝，或认为字典单次操作受保护就能让库存扣减这类复合操作安全。[B25](05_参考来源与版本说明.md#b25)[B27](05_参考来源与版本说明.md#b27)

## 19. 一致性、事务与幂等

<a id="q19-1"></a>

### Q19.1 分布式事务如何选型，2PC 与 Saga 差在哪？

原题定位：P005「分布式事务怎么操作」；P020「多阶段分布式一致性」。后者未给协议名，不强行解释为 2PC。

**核心答案：**先判断能否收敛到一个本地事务；不能再讨论跨资源协调。2PC 通过准备、提交阶段协调参与者，依赖各资源协议支持，并增加故障恢复和资源持有成本；MySQL XA 是具体支持之一。Saga 把流程拆成已提交的本地事务，失败时执行补偿，因此中间状态可能被观察，不提供与单库事务相同的隔离性。[B30](05_参考来源与版本说明.md#b30)[B31](05_参考来源与版本说明.md#b31)

**建议：**资金或库存的强约束优先放在权威服务事务内；跨服务长流程可用 Saga 配合状态机、超时、补偿和人工兜底。补偿是新的业务动作，不是物理回滚，例如退款不等于支付从未发生。常见错误是称 Saga 天然强一致，或宣称所有系统、消息队列都能无条件加入同一个 XA 事务。[B30](05_参考来源与版本说明.md#b30)[B31](05_参考来源与版本说明.md#b31)

<a id="q19-2"></a>

### Q19.2 幂等表是什么，怎样避免重复请求产生重复效果？

原题定位：P008「幂等表是什么」。

**核心答案：**幂等表记录业务请求的去重键、处理状态及必要结果，让相同请求重复到达时只产生一次预期业务效果。建议用租户、操作类型、业务请求 ID 组成唯一键，并存参数摘要，避免同一个键被用于不同请求。最重要的是去重记录与业务修改在同一本地事务完成，而非先查询“没有”再无保护插入。[B21](05_参考来源与版本说明.md#b21)[B32](05_参考来源与版本说明.md#b32)

**故障处理：**请求超时不代表失败；重试应返回已完成结果，或明确处理中并允许查询。跨外部接口时，本地幂等表无法独自保证外部扣款一次，需要对方幂等键、状态查询或补偿。保留时间按重试窗口与业务追溯要求确定。常见错误是只在 Redis 放短 TTL 标记，过期后旧请求再次执行，或把重复请求一律返回成功而忽略此前失败。[B21](05_参考来源与版本说明.md#b21)[B31](05_参考来源与版本说明.md#b31)

<a id="q19-3"></a>

### Q19.3 最终一致性如何落地，outbox 可以保证什么？

原题定位：P019「分布式最终一致性」。

**核心答案：**最终一致性不是“迟早自动正确”，而是允许短期不同步并设计收敛机制。outbox 把业务变化和待发布事件放入同一数据库事务，解决该本地边界的双写缺口；投递进程仍可能在发送后、标记成功前崩溃，所以消息可以重复，消费者仍需幂等。[B21](05_参考来源与版本说明.md#b21)

**建议：**以业务状态机定义允许的中间状态、收敛时限和失败处理，按业务键及版本处理乱序；配合重试退避、死信、积压告警和定期对账。监控从业务提交到消费生效的延迟，而不只看队列在线。常见错误是无限重试坏消息阻塞正常事件，或把已入队当成下游已完成，更不能仅靠发布顺序保证多消费者的完成顺序。[B21](05_参考来源与版本说明.md#b21)[B31](05_参考来源与版本说明.md#b31)

<a id="q19-4"></a>

### Q19.4 数据库事务能直接保证缓存、消息与外部调用一致吗？

原题定位：P015「mysql事务隔离级别」；P019「分布式最终一致性」的跨资源扩展。

**核心答案：**数据库事务只覆盖实际参与的资源，普通 Redis 写、Kafka 发消息或 HTTP 调用不会因为处于同一段代码就一起提交回滚。数据库与缓存可选择提交后失效、TTL 和重建，但提交后删除失败或读者回填旧值仍可造成陈旧；这是容许窗口下的策略，不是严格原子协议。[B13](05_参考来源与版本说明.md#b13)[B21](05_参考来源与版本说明.md#b21)

**建议：**先指定权威数据源及一致性预算；对关键查询可绕过缓存，对更新通过事件补偿失效，必要时用版本阻止旧值覆盖。重复删除只能缓解部分竞态，固定“延迟双删”时间不能证明一致性。外部调用若已产生不可回滚副作用，要使用幂等接口、结果查询和业务补偿，而不是认为数据库回滚能撤销外部世界。[B21](05_参考来源与版本说明.md#b21)[B31](05_参考来源与版本说明.md#b31)

## 20. C++ 与 STL

<a id="q20-1"></a>

### Q20.1 vector 前后追加有什么不同，deque 为什么不同？

原题定位：P004「cpp 的 vector 前后追加的区别，stl 什么数据结构前后追加一样」。

**核心答案：**vector 连续存储，尾部 `push_back` 摊销 O(1)，扩容时会搬移元素；头部插入需移动现有元素，是 O(n)，不能将尾部复杂度套用到头部。deque 支持两端常数时间插入，并支持随机访问，但不保证整体连续存储；它的两端 O(1) 不意味着 vector 头插也 O(1)。[B33](05_参考来源与版本说明.md#b33)[B34](05_参考来源与版本说明.md#b34)

**取舍：**需要连续内存、缓存局部性和与连续缓冲接口交互时优先 vector；频繁双端操作时可考虑 deque。vector 扩容会使所有相关引用和迭代器失效；不扩容插入也会影响插入点及之后的迭代器。deque 两端插入不使既有元素引用失效，但会使迭代器失效，不能只背复杂度而忽略生命周期。[B33](05_参考来源与版本说明.md#b33)[B34](05_参考来源与版本说明.md#b34)

<a id="q20-2"></a>

### Q20.2 智能指针有哪些，shared_ptr 就线程安全吗？

原题定位：P034「cpp智能指针有哪些」。

**核心答案：**`unique_ptr` 表示独占所有权，可移动不可复制；`shared_ptr` 共享生命周期；`weak_ptr` 不增加强引用计数，可通过 `lock` 尝试取得临时所有权，常用于打破循环引用。优先明确唯一所有者，再在确实需要共享生命周期时使用 shared_ptr，不把它当通用裸指针替换器。[B35](05_参考来源与版本说明.md#b35)

**并发边界：**不同 shared_ptr 实例共享控制块时，引用计数管理的并发安全不等于被指对象线程安全；同一个 shared_ptr 变量的并发读写也需要同步，或使用 C++20 的 `atomic<shared_ptr<T>>`。后者仍不保护对象内容。常见错误包括用同一个裸指针分别创建两个控制块导致重复释放，以及互相强引用形成泄漏。[B35](05_参考来源与版本说明.md#b35)[B36](05_参考来源与版本说明.md#b36)

<a id="q20-3"></a>

### Q20.3 C++ 多态底层是什么，虚析构为什么重要？

原题定位：P034「C++多态的底层机制是什么」。

**核心答案：**语言规范规定虚函数通过对象的动态类型选择最终覆盖函数；常见 ABI 以虚表和虚表指针实现，但具体数量、位置与布局不是所有编译器共同的语言保证。编译器在能确定目标时还可去虚化，所以不应宣称每次虚调用都必然多一次固定开销。[B37](05_参考来源与版本说明.md#b37)[B38](05_参考来源与版本说明.md#b38)

**建议：**需要经基类指针销毁派生对象的接口，通常应有虚析构；使用 `override` 帮助发现签名错误。构造、析构阶段的虚调用不会像“完整的最派生对象”那样分派，应避免依赖这种行为。常见错误是按值传递基类导致切片，或通过无合适虚析构的基类指针 delete 派生对象而产生未定义行为。[B37](05_参考来源与版本说明.md#b37)[B38](05_参考来源与版本说明.md#b38)

<a id="q20-4"></a>

### Q20.4 C++ 开发中重点防哪些问题？

原题定位：P020「cpp 开发过程中有什么需要注意的，」；P005「cpp了解的多吗」。后者为宽泛问法，不据此虚构具体经验。

**核心答案：**重点管理所有权、对象生命周期、异常安全和数据竞争。通过 RAII 把资源释放绑定到对象生命周期，用值语义和标准容器减少手工内存管理；拷贝、移动以及返回引用都要明确被引用对象能活多久。无同步的冲突内存访问可能构成数据竞争，带来未定义行为，不能把“测试暂时正常”当正确性证明。[B39](05_参考来源与版本说明.md#b39)[B40](05_参考来源与版本说明.md#b40)

**建议：**在 CI 中用警告、静态分析和适当 sanitizer 捕获越界、悬垂和竞争，关键接口明确异常与错误返回策略。异常安全区分不泄漏且保持有效状态的基本保证，与失败时不改变可观察状态的强保证。常见错误是返回局部对象引用、容器改动后继续使用失效迭代器，或仅加引用计数而不保护业务字段。[B33](05_参考来源与版本说明.md#b33)[B39](05_参考来源与版本说明.md#b39)[B40](05_参考来源与版本说明.md#b40)

## 21. 消息队列与 Kafka

<a id="q21-1"></a>

### Q21.1 Kafka 适合什么场景，和其他 MQ 怎么比较？

原题定位：P005「kafka用在哪儿？」；P018「Kafka用在什么场景，怎么分区」「Kafka 和其他MQ消息队列相比，差异是什么？」。

**核心答案：**Kafka 是基于分区日志的事件流平台，适合高吞吐事件采集、可回放的数据管道及流处理。消费者维护自己的位置，数据保留与是否已被某个消费者读取通常分离，因此多个消费组可独立读取。不能只把它描述为“消费即删除的任务队列”。[B41](05_参考来源与版本说明.md#b41)

**取舍：**按吞吐、延迟、回放、顺序、路由、延迟消息和运维成本选择，不应宣称 Kafka 在所有指标上优于所有 MQ。复杂路由或任务调度需求可能需要其他方案，但具体对比必须指定产品与版本。生产者确认、复制及保留设置共同影响可靠性与成本，不能只凭产品名字承诺消息永不丢失。[B41](05_参考来源与版本说明.md#b41)[B42](05_参考来源与版本说明.md#b42)

<a id="q21-2"></a>

### Q21.2 如何分区，Kafka 能保证全局顺序吗？

原题定位：P018「Kafka用在什么场景，怎么分区」。

**核心答案：**Kafka 的日志顺序以分区为单位，没有天然跨分区总顺序。需要同一订单有序，通常以订单 ID 作为稳定路由键，让相关事件进入同一分区；但分区日志有序不等于消费者并行执行的副作用完成有序，仍需按业务键串行处理或校验版本。[B41](05_参考来源与版本说明.md#b41)[B42](05_参考来源与版本说明.md#b42)

**建议：**分区数综合吞吐、消费并行度、热点和运维开销决定，不能无限增加。扩分区可能改变基于 key 的映射，历史与新事件的有序衔接需设计。幂等生产者可帮助处理重试，但如果关闭幂等且允许多个在途请求，重试可能乱序；以实际生产者配置核实，而非把“带 key”当作端到端顺序证明。[B42](05_参考来源与版本说明.md#b42)[B43](05_参考来源与版本说明.md#b43)

<a id="q21-3"></a>

### Q21.3 新增消费者后怎么分配分区，消费者越多越快吗？

原题定位：P018「Kafka 里新增一个消费者，分区是怎么分配的？」。

**核心答案：**同一消费组内，一个分区在正常稳定分配状态下由一个消费者负责；多个消费组可独立消费同一分区。组成员加入、离开或订阅变化会触发分配调整，因此同组消费者超过可分配分区数后，可能有人空闲。具体分配取决于订阅、分配器和组协议，不能只回答“平均分”。[B41](05_参考来源与版本说明.md#b41)[B44](05_参考来源与版本说明.md#b44)

**版本边界与建议：**Kafka 4.0 起新的 Consumer rebalance protocol 已正式可用，但客户端需按实际配置采用；不要把经典客户端分配与新协议的服务端分配混讲。扩容前看 lag、处理耗时和下游容量，正确处理分区撤销、在途任务与 offset 提交。频繁重平衡或拉取间隔超限可能抵消扩容收益，分配协议也不代替业务幂等。[B44](05_参考来源与版本说明.md#b44)

<a id="q21-4"></a>

### Q21.4 重复消费正常吗，Exactly-once 覆盖外部数据库吗？

原题定位：P005「消息队列重复消费正常吗？」。

**核心答案：**业务效果完成后、offset 提交前崩溃，会导致重启后重复消费，这是常见至少一次交付行为；若先提交 offset 再做业务，则可能漏处理。Kafka 的幂等生产者解决生产重试重复，事务可把 Kafka 输出记录与消费位置一起提交，配合 `read_committed` 实现相应 Kafka 读—处理—写边界内的 exactly-once。[B42](05_参考来源与版本说明.md#b42)[B43](05_参考来源与版本说明.md#b43)

**外部边界：**Kafka EOS 不自动覆盖普通外部数据库写入、发短信或支付扣款。可在外部数据库同一事务内完成事件去重与业务更新，再提交 offset；崩溃重投由去重处理，或采用明确支持协调的连接器方案。不要以“开启事务”宣称所有外部副作用恰好一次，也不要为了消除重复而提前提交位置牺牲不丢处理。[B21](05_参考来源与版本说明.md#b21)[B42](05_参考来源与版本说明.md#b42)
