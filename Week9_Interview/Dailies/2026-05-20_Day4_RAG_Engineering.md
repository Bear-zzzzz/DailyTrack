## 🧠 模块 1：多格式文档接入 RAG（小红书 Q1）

### 问题
知识库原始数据不是 markdown，而是 PDF、PPT、图片或者网页，你会怎么处理进 RAG 系统？

### 处理流程

```
Step 1：按格式提取内容
  PDF / PPT → 提取标题、章节、表格、页码
  图片      → OCR 识别
  网页      → 提取正文和元数据（去掉导航栏、广告）

Step 2：统一清洗
  去噪、去页眉页脚、去乱码

Step 3：语义分块
  按语义切分（不是固定字数硬切）

Step 4：添加元数据
  来源 + 时间 + 文档层级（章节路径）

Step 5：生成 embedding，建索引
```

**三个收益**：
- 召回更稳定（元数据辅助过滤）
- 来源可追溯（引用时知道从哪来）
- 权限可控（按来源做访问控制）

## 🧠 模块 2：三种检索机制（小红书 Q2）

### 常用检索机制

| 类型 | 原理 | 适合场景 |
|------|------|---------|
| 关键词检索 | 字面匹配（BM25） | 专业术语、精确匹配 |
| 向量检索 | 语义相似度 | 措辞不同但意思相近 |
| 混合检索 | 关键词 + 向量融合 | 兼顾字面和语义，通常最稳定 |

**线上系统实践**：多路召回 + 重排序，不是单路召回。

## 🧠 模块 3：RAG 双层评估指标（小红书 Q3）

### 问题
RAG 评价指标一般怎么设计？

### 两层评估

**检索侧**（召回的对不对）：
- Recall@K：前 K 个结果里有多少是相关的
- MRR（Mean Reciprocal Rank）：第一个相关结果排在第几
- NDCG：综合考虑相关性和排名位置

**生成侧**（答案质量）：
- 答案相关性：回答是否切题
- 忠实度（Faithfulness）：答案是否基于召回内容，而非模型自己编的
- 上下文利用有效性：是否充分利用了检索到的证据

**核心陷阱**：
> "听起来对"是不够的——模型可能生成流畅但事实错误的回答

## 🧠 模块 4：RAG vs 微调的选型逻辑（小红书 Q4）

### 问题
为什么很多场景会优先选 RAG，而不是直接微调大模型？

### 核心原因

```
业务知识更新快
  → 微调：成本高 + 周期长 + 知识变化就要重训
  → RAG：更新知识库即可，无需重训

知识类型不同
  → 私域知识、频繁更新、需要溯源  → RAG
  → 风格调整、任务习惯、领域能力边界 → 微调
```

**实践做法**：RAG 和微调常结合使用，不是二选一。

## 🧠 模块 5：两级缓存设计（小红书 Q6）

### 问题
为什么 AI 应用里经常需要做两级缓存？

### 原因
AI 链路中 embedding / 检索 / 重排 / 生成 每步成本高、延迟高，重复请求很多。

### 两层设计

```
Level 1：本地缓存（进程内）
  → 命中最快，适合超高频热点

Level 2：Redis（多实例共享）
  → 跨进程共享，适合分布式场景
```

**收益**：减少重复 embedding 计算 + 重复 LLM 调用，降低成本，稳定响应时间

**三个坑**：缓存穿透 + 热点 key 打爆 + 版本失效（知识库更新后旧缓存要清理）

## 🧠 模块 6：智能客服完整链路设计（小红书 Q7）

### 问题
如果要做一个智能客服类 AI 应用，整体链路怎么设计？

### 四路分流

```
用户问题
  ↓
问题分类
  ├── FAQ 类           → 模板直接回复
  ├── 知识类问答        → RAG 检索 + 生成
  ├── 工具调用类        → 查订单 / 查账户 / 查发货
  └── 高风险 / 低信任  → 直接转人工
```

### 核心链路必备组件

```
会话管理    多轮上下文维护
权限校验    用户身份 + 操作权限
敏感词过滤  输入输出双向过滤
日志追踪    全链路 trace
效果评估    在线指标 + 离线回放
```

## 🧠 模块 7：PGVector vs ES vs MySQL 技术选型（小红书 Q8、Q9、Q10）

### PGVector vs ES（Q8）

| | PGVector | Elasticsearch |
|---|---|---|
| 适合 | 业务数据本身在 PG，快速部署 | 全文 + 向量混合检索 |
| 优势 | 集成维护成本低，结构化和向量统一管理 | 混合检索能力强 |
| 适用场景 | 数据在 PG + 快速部署 | 需要强全文检索能力 |

### MySQL vs ES 分工（Q9）

```
MySQL  → 主业务数据（事务型、关系型、强一致）
        存：用户、配置、权限、任务记录

ES     → 搜索层（全文检索、模糊匹配、聚合分析）
        做：文本搜索、内容检索、日志分析
```

**关键点**：两者不是替代关系，是主存储和搜索层的分工。

### ES 为什么用倒排索引（Q10）

**问题**：全文检索数据量大，顺序扫描代价极高。

**倒排索引原理**：
```
建立"词 → 文档列表"的映射
查询时：
  1. 直接定位包含该词的文档列表
  2. 再做过滤和打分
  无需扫描全部文档
```

**效果**：无论关键词查询、短语匹配还是多条件组合搜索，效率都远高于顺序扫描。
