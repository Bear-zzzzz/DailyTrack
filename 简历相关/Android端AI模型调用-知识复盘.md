# Android 手机端 AI 模型调用（云端链路）— 知识复盘

---

## 知识体系速查

### 端到端延迟拆解

```
用户操作
  ├─ 客户端预处理（resize/编码/序列化）     5~50ms
  ├─ DNS 解析                               20~200ms
  ├─ TCP + TLS 握手（首次/无连接池）         100~300ms
  ├─ 请求上传（图片/音频/文本）              50~500ms
  ├─ 服务端排队等待                          0~2000ms
  ├─ 模型推理                                100~5000ms
  ├─ 响应下载                                50~500ms
  └─ 客户端后处理（解析/渲染）               5~30ms
```

### 功耗拆解

```
单次云端 AI 调用功耗:
├── Radio 唤醒（IDLE → DCH）           ← 固定能耗
├── 数据上传/下载传输                   ← 与数据量成正比
├── Radio 尾部时间（DCH → FACH → IDLE） ← ~30s 固定能耗
├── CPU 编解码/序列化
└── 屏幕/渲染（等待期间亮屏）

关键: 小请求 Radio 尾部是大头；大请求传输是大头；频繁调用 Radio 反复唤醒
```

### 核心优化手段速查

| 维度 | 关键点 |
|------|--------|
| **实时性** | SSE 流式（首 token <500ms）→ 连接池复用 → 请求取消 → 弱网降级 |
| **传输** | Gzip 压缩 → 图片压缩 → WebP → Protobuf |
| **连接** | 连接池复用 → HTTP/2 多路复用 → HTTPDNS |
| **功耗** | 批量合并 → 推送替代轮询 → WorkManager 条件触发 → 缓存减少请求 |
| **缓存** | 结果缓存 → session 上下文 → 离线队列 |
| **系统适配** | Doze 用 WorkManager → 温控降频 → 网络状态监听降级 |
| **监控** | 首 token 延迟 → 端到端 P95 → 成功率 → 日均功耗 |

## 问答复盘

### Q1: LLM 云端流式输出（SSE）和非流式区别？为什么改善体验？首 token 延迟是什么？

**我的回答：**

流式可以分块发送信息，而不需要等模型全部返回后一起输出，提高了体感上的响应速度。首 token 延迟，就是用户发出请求后，第一次打印回复的时间。

**点评：** ⭐⭐⭐⭐ 答得好

补精确化：
- 首字节时间（TTFB，Time To First Byte/Token）：从**发出请求到收到第一个 token** 的耗时，是 LLM 体验的**核心指标**。
- 流式的本质：用户**感知延迟**从"全部生成完"变成"首 token"，体感上从等 8 秒变成等 0.3 秒。

**优化点：** 面试中强调"感知延迟从全部生成完变成首 token"这个本质，并明确 TTFB 是 LLM 体验核心指标。

---

### Q2: 云端 AI 调用功耗来自哪里？为什么轮询比推送更耗电？

**我的回答：**

主要来自发送网络请求后，蜂窝网络 IDLE→DCH→FACH 的过程，会经历 30s 的全功耗时期。因为轮询 30s 就会有一次耗能，服务有结果时再推送，可以批量返回。

**点评：** ⭐⭐⭐⭐ 基本正确

需精确化：
- "推送可以批量返回"——这不是核心。核心是：**轮询每次都唤醒 Radio，即使没数据也付 30s 尾部功耗；推送只在有数据时才唤醒 Radio，无数据时 Radio 一直 IDLE**。

**优化点：** 面试中强调"轮询无数据也付 30s 尾部功耗，推送只在有数据时唤醒"这个对比，不是"批量返回"。

---

### Q3: OkHttp 连接池复用省什么？10 轮对话用和不用区别多大？

**我的回答：**

省的 TCP 连接建立、TLS 握手的经历；区别在于，少了 9 次 TCP TLS 握手。

**点评：** ⭐⭐⭐⭐ 答得好

可补数字更有说服力：每次 TCP+TLS 握手约 **100~300ms**，10 轮省 9 次 = 省 **900ms~2.7s**。

**优化点：** 面试中说出"每次握手 100~300ms，10 轮省 900ms~2.7s"这个量化收益。

### Q4: 用户快速切换 3 个问题（A→B→C），不处理会怎样？正确做法？

**我的回答：**

3 个问题排队处理；正确的是保留最新一次的会话，进行请求。

**点评：** ⭐⭐⭐ 方向对，缺关键场景

"排队处理"描述不准确，实际不处理时的问题是：

| 问题 | 后果 |
|------|------|
| 3 个请求同时发出 | 浪费带宽 + Radio 时间 |
| 响应可能乱序到达 | A 的结果覆盖 C 的，UI 混乱 |
| 服务端排队 | 3 个请求占 GPU 资源 |

正确做法的完整描述：
1. **取消前一个请求**：`currentCall?.cancel()`
2. **只发最新的**：A 发出→用户问 B→cancel A，发 B→用户问 C→cancel B，发 C
3. **丢弃过期响应**：响应回来时检查是否是当前请求，不是就忽略

**优化点：** 面试中说出"取消旧请求 + 丢弃过期响应"两个动作，并说明不处理的三个后果（浪费带宽、响应乱序、占用服务端资源）。

### Q5: Doze 对云端 AI 调用的影响？后台任务该用什么？为什么不用 AlarmManager？

**我的回答：**

Doze 模式会使设备进入休眠状态，如果不处理不会发生 AI 调用。应该用 WorkManager 的方式处理，让系统统一调度。如果用 AlarmManager + 轮询，系统会唤醒，功耗会提高。

**点评：** ⭐⭐⭐ 方向对，缺关键限制

缺的关键点：
- **Doze 的具体限制**：不只是"休眠"，是**延迟网络访问**（请求被排队到维护窗口才放行）+ **暂停 WorkManager 任务**。
- **为什么 WorkManager 比 AlarmManager 好**：不只是"系统统一调度"，核心是 WorkManager 的**条件触发**（充电+WiFi+空闲才执行）+ **系统批量合并**（多个 App 的任务攒到维护窗口一起执行，减少 Radio 唤醒次数）。
- **紧急场景的例外**：真正紧急的消息可以用 **FCM high priority** 推送（可绕过 Doze），但不能滥用。

**优化点：** 面试中说清三点——① Doze 延迟网络访问；② WorkManager 条件触发+批量合并；③ 紧急用 FCM high priority。

| 题 | 评价 | 待补强 |

| 1 | ⭐⭐⭐⭐ 答得好 | 补 TTFB 精确定义 |
| 2 | ⭐⭐⭐⭐ 基本正确 | "批量返回"改为"有数据才唤醒" |
| 3 | ⭐⭐⭐⭐ 答得好 | 补 100~300ms/次数字 |
| 4 | ⭐⭐⭐ 方向对 | 补不处理的三个后果 + 丢弃过期响应 |
| 5 | ⭐⭐⭐ 方向对 | 补 Doze 具体限制 + WorkManager 批量合并 + FCM high priority |

**整体：云端 AI 调用的核心概念掌握扎实，"不处理会怎样"的后果分析和工作机制细节需补强。**

重点记三个：
1. **推送 vs 轮询**：轮询无数据也付 30s 尾部功耗，推送有数据才唤醒
2. **请求取消**：取消旧请求 + 丢弃过期响应，防乱序/浪费
3. **Doze + WorkManager**：Doze 延迟网络，WorkManager 条件触发+批量合并
