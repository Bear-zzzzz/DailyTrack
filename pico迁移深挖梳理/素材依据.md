## 使用边界

- CPU 数据是均值，不是峰值；百分比下降是相对变化，不是百分点。
- 资源占用应明确指标。当前给出的 MB 数据是内存，不是所有资源。
- 目标与早期基准不能与整体升级效果混用，Harness 90%+ 与 30.2%需分清范围。
- 团队整体结果不等于个人模块独立收益；具体贡献归因待补。
- 一期材料记录已随 OTA 9.3 内测 1 上线，回退策略当时预计随内测 2 验证；最新状态尚未核验。
- 线上 PicoClaw 样本较少，规模化效果仍待验证。设备、样本量、采样、CPU 与内存统计口径需补充。
- 一期复用部分既有 Skill 运行环境；完全去除解释器、全量切流与旧引擎下线属于后续目标，不能提前写成成果。
- Go 有运行时、调度器和 GC；编译期插件装配不等于故障隔离沙箱。
- 已读取正文及进展中的三张关键图表，尚未核验现行源码和原始性能报告。

## 插件能力校准：扩展点与统一 Plugin 框架

本次补充核对了 Sipeed 官方 main 分支 README、Hooks 文档，以及本机 `liclaw-pico/pkg/liclaw/plugin` 源码。此前“尚未核验源码”仅对应性能与整体方案；插件层现已做局部源码核对，未作全量代码审计。

- 上游支持 Skills、MCP，以及进程内/进程外 Hooks。Hooks 文档包含 `MountHook`、`RegisterBuiltinHook` 和 JSON-RPC over stdio，这些确实是扩展机制，不能说上游完全无法扩展。
- 上述能力不能直接等同于 OpenClaw 风格统一 Plugin 接口、业务注册 API 和插件装配层。此次官方材料未确认一套与项目自研层相同的通用 Plugin 包管理体系。
- 本机 fork 的 `pkg/liclaw/plugin/plugin.go` 定义 `Plugin.Meta()`、`Plugin.Register(api)`，统一 API 转接原生工具注册与 Hook 挂载，并提供 Config、Workspace 和 Bridge 依赖；这是自研业务插件层。
- 插件通过 `init()` 自注册与匿名导入进入二进制，启动时由 `Assemble` 装配；不是 Go `.so` 动态插件，也不能表述为无需重新编译安装任意代码插件。
- 当前统一 API 没有 `RegisterChannel`；Channel 使用原生工厂注册点。`Service` 为预留接口，不能据此宣称完整后台服务生命周期已经落地。
- 源码注册表采用互斥锁和快照副本，不应将二期“冻结只读”规划当成当前已验证实现。

适合面试的表述：**“PicoClaw 原生有工具注册、Hooks、Skills/MCP 等扩展点，我们在这些能力之上补建统一业务插件接口和注册装配层，方便存量插件模块化迁移。”**个人实现范围仍以用户确认的职责为准。
