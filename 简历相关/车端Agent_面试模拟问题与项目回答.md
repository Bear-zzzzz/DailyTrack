## 项目描述草稿

**项目名称：车端 Agent 引擎轻量化与执行链路优化（OpenClaw → PicoClaw）**

### 1. 问题场景

车端理想同学通过 Agent 承接复杂任务和工具自动化执行。原方案基于 OpenClaw，在资源受限的座舱设备上存在运行时与依赖负担、常驻资源占用、启动开销以及执行链路耗时问题，需要同时优化资源和响应体验。迁移还涉及已有业务协议、工具、Skill、上下文、安全与遥测能力，不能只替换引擎而损失必要业务行为。

### 2. 目标与约束

在保持核心业务能力与上层使用方式兼容的前提下，降低内存、CPU 和启动开销，缩短端到端任务耗时；建立可扩展的业务插件接入方式及双引擎对照、灰度回退能力，支持分阶段迁移。

量化目标属于早期评估，简历优先写一期记录的实际效果。一期保留部分既有 Skill 运行环境；去除所有 Python/Node.js 依赖、全量切流与旧引擎下线不能提前写成已完成成果。

### 3. 关键做法（项目整体，需按个人职责筛选）

- **引擎与执行编排：**将核心执行链迁入 PicoClaw/Go，统一 AgentLoop 内上下文、模型、工具与回复阶段，减少跨层转发和重复处理。
- **上下文与工具性能：**模型调用前裁剪冗余上下文，历史 Skill 正文替换为来源记录；文件按范围读取，搜索结果减少中间对象与重复序列化；精简流式处理和高频工具收发链路。
- **兼容与插件体系：**保持业务协议和 Skill 使用方式兼容，通过统一接口、独立子包、注册与编译期装配迁移业务模块，降低核心框架侵入。
- **评测与发布保障：**建设双引擎日志对照及单 Query 链路下钻能力，结合线上指标、分阶段切换和回退验证迁移效果。进展材料记录回滚策略已开发、当时预计随内测 2 验证；实际发布状态需确认。

### 4. 达成效果（材料记录的项目整体结果）

一期已随 OTA 9.3 内测 1 上线。内存均值由 **328.65 MB 降至 36.68 MB（降低 88.8%）**，CPU 均值由 **5.09% 降至 0.66%（相对降低 87.0%）**，端到端平均耗时由 **9.23 秒降至 6.92 秒（降低 25.0%）**。评测支持双引擎自动化对照，材料记录差异定位由天级缩短至小时级。规模化线上效果仍需随灰度放量持续验证。

## P0｜项目与架构

### Q01. 介绍一个你做过的 Agent 项目，你解决了什么问题？

**口述参考回答：** 这个项目是车端 Agent 的引擎升级与性能优化。原有引擎基于 OpenClaw，在复杂任务中存在 Harness 层耗时较长、资源占用高和启动慢的问题。团队评估后决定迁移到 PicoClaw。我主要负责插件系统框架建设和功能插件移植，支持原有业务接入方在保持原有使用方式的前提下无感切换。最终，项目整体内存均值从 300 多 MB 降到约 37 MB，CPU 均值从约 5% 降到 0.7%，端到端平均耗时降低约 25%。

**材料依据：** 用户确认个人职责；《端侧 LiClaw Harness 升级专项》提供迁移背景与兼容目标；《LiClaw 升级专项进展及效果》记录项目整体指标。

**待补充：** 插件框架的具体设计、亲自迁移的功能插件、无感切换的验证方法，以及个人工作与整体性能收益的关系。原始指标为内存均值 328.65→36.68 MB、CPU 均值 5.09%→0.66%；不能将均值称为峰值，未核实启动收益不补具体数字。

**继续追问：** 你亲自解决的最难问题是什么？

### Q02. 如何为资源受限的端侧设备选择 Agent 框架？为什么不直接优化现有方案？

**口述参考回答：** 我会先列硬约束：设备资源、部署条件、必须保留的模型与工具能力、维护成本，再比较现有框架裁剪、换轻量框架和自研三类方案。这个项目的评估最终选择 PicoClaw：已有 Agent Runtime 能力和部署基础，能降低重新补齐基础功能的成本，同时通过 Go 编译部署减少原有 JS 运行时和依赖的负担。但语言不是唯一理由，还要看业务适配后的实际收益；框架选择以具体版本、许可证核验和基准测试为依据。

**材料依据：** E：候选方案筛选与选型；S：兼容约束。

**待补充：** 必须补：你实际参与比较的候选、最小验证过程，以及为何局部优化不足。

**继续追问：** 如果裁剪 OpenClaw 就能满足目标，还需要迁移吗？

### Q03. 从用户请求到真实工具执行，一个 Agent 的完整链路是什么？

**口述参考回答：** 入口先建立用户、会话和任务关联，再构建上下文与可用工具集合。AgentLoop 调用模型，模型返回文本或工具调用；执行端做参数、权限和状态检查，调用工具并把结构化结果送回模型，必要时继续下一轮，最后返回结果并记录状态。模型负责提出动作，Runtime 负责执行生命周期，业务执行端确认实际效果。我们把上下文、模型、工具、回复等阶段统一在 Go AgentLoop 内组织，减少阶段间转发和重复处理。

**材料依据：** R：统一 AgentLoop 与执行链路；E：Harness 定义。

**待补充：** 必须补：当前入口、五阶段具体划分、停止条件及工具执行端。

**继续追问：** 工具返回成功，是否等于用户任务完成？

### Q04. 迁移一个 Agent 引擎，最难的部分是什么？

**口述参考回答：** 最难的是保持行为语义，而不只是把接口或语言换掉。需要建立能力矩阵，对照模型接入、工具、流式事件、会话、记忆、安全、遥测和配置行为，再验证超时、取消与错误路径。这个项目采用业务协议和 Skill 使用方式兼容、业务插件迁移、双引擎对照及分阶段切流来控制风险。相同工具名和 Schema 是起点，还要检查结果、错误、副作用和生命周期语义。

**材料依据：** E：能力覆盖与迁移清单；R：工程体系。

**待补充：** 必须补：一个实际兼容问题、旧行为、新实现与回归证据。

**继续追问：** 有没有接口不变但行为变化的例子？

## P0｜性能与上下文

### Q05. 你会怎样定位并降低一个常驻 Agent 的内存和 CPU 占用？

**口述参考回答：** 先区分空闲、启动、单任务、并发和长时间运行，再测进程内存、堆、CPU、分配和队列变化，判断运行时基础负担、业务对象、缓存或泄漏分别占多少。项目采取核心链路迁入 Go、按范围读取文件、减少中间对象和重复序列化等措施。整体升级后的内存均值下降 88.8%、CPU 均值相对下降 87.0%；这些是多项改造的整体效果，不能全部归因于换语言。

**材料依据：** R：资源指标和原生化、按需读取措施。

**待补充：** 必须补：设备、内存统计口径、CPU 口径、采样方法及实际 profiling 证据。

**继续追问：** 怎样证明是运行时负担而不是内存泄漏？

### Q06. Agent 响应很慢，你如何分析和优化端到端延迟？

**口述参考回答：** 先用统一时间线拆出排队、上下文构建、模型等待与生成、工具执行和反馈，定位关键路径；流式或并行区间要避免重复相加。项目整体平均耗时从 9.23 秒到 6.92 秒，分层记录模型 7.66→5.93 秒、工具 1.14→0.69 秒、Harness 0.43→0.30 秒。因此优化同时涉及输入上下文、工具路径和执行编排。还要看 P50、尾延迟和失败率，不只看均值。

**材料依据：** R：效果图表和链路改造。

**待补充：** 必须补：各层计时起止、并行区间、样本和异常请求计入口径。

**继续追问：** 哪个改动贡献最大？怎么隔离验证？

### Q07. 耗时主要在云端模型，优化本地框架有什么意义？

**口述参考回答：** 单纯减少本地调度开销，收益受该段占比限制。但本地框架还决定模型读多少输入、调用多少轮，以及工具结果如何组织，这些会影响模型侧耗时。我们每次模型调用前整形上下文，截短已消费工具结果、用来源记录替代历史 Skill 正文、裁剪旧轮次，并精简流式处理。文档记录模型层耗时下降 22.6%，但要进一步用输入 Token、调用轮次和对照实验解释，不能把它直接说成模型推理速度提升。

**材料依据：** R：上下文与模型链路优化、模型层指标。

**待补充：** 必须补：模型和网络是否一致，Token/轮次变化及单变量实验。

**继续追问：** 如果模型和输入都不变，框架还能让模型更快吗？

### Q08. 如何缩短上下文，同时保证 Agent 不丢关键信息？

**口述参考回答：** 先按信息类型管理：保留用户目标、约束、授权、已执行动作、未完成任务及关键事实；大段原文和已消费工具结果用摘要、来源与定位信息代替，必要时重读。我们在每次模型调用前进行整形，并把历史 Skill 正文替换为来源记录。文件工具按偏移和范围读取，文档记录默认范围为 64 KB。减少输入后要验证约束保留、事实错误和任务完成率，重要状态不能只依赖自然语言摘要。

**材料依据：** R：上下文整形和范围读取。

**待补充：** 必须补：裁剪规则、来源记录结构、重读触发及验证用例。

**继续追问：** 被裁掉的工具结果下一轮又需要怎么办？

### Q09. 如何优化工具链路，而不牺牲安全和扩展性？

**口述参考回答：** 先区分业务工具执行耗时与框架转发开销，再减少不必要的层级、序列化和重复检查。项目把高频车端工具收发内置引擎，统一会话绑定、回执校验、超时与取消；文件读取仍保留工作区约束、路径白名单和沙箱过滤，搜索结果解析后直接返回格式化文本。工具层耗时记录为 1.14→0.69 秒。安全条件和结果验证仍需落实，不能因为调用进程内直通就假设安全。

**材料依据：** R：工具链路与读取、搜索优化。

**待补充：** 必须补：你负责的工具、实际减少的转发步骤、边界检查和兼容测试。

**继续追问：** 内置工具会不会让框架与业务重新耦合？

### Q10. 如何证明一次性能优化有效，而不是测试条件变了？

**口述参考回答：** 固定设备、版本、模型、请求集、工具行为和网络条件，区分冷启动、热启动和缓存状态；重复运行，报告样本量、资源、耗时分布及业务成功率。再把引擎替换、上下文优化、工具改造分别开关对照，识别贡献和交互影响。我们的进展文档有整体升级结果，评估文档也有早期基准，但两套数字不能混用；Harness 90%+目标与整体结果中的 30.2%需要说明测试范围和条件。

**材料依据：** E：早期基准；R：整体效果与样本限制。

## P0｜插件架构与评测

### Q11. 如何设计一个容易扩展、又不会拖慢执行的插件体系？

**口述参考回答：** 把变化点抽象为接口，让业务实现放在独立子包，通过注册表和装配器注入核心引擎，避免业务直接修改主循环。项目采用统一 Plugin 接口、声明式注册和编译期集成；二期规划进一步扩展到 AgentLoop、Channel、Provider 等。进程内模块化可以减少调用开销，但仍要明确依赖、调用顺序、错误策略和并发边界。它本身不等于隔离沙箱，阻塞或 panic 是否可隔离需要另外设计。

**材料依据：** S：一期组件化及二期全域插件化；R：一期工程体系。

**待补充：** 必须补：一期实际接口、注册顺序、冲突检查和错误处理；沙箱实现未核实。

**继续追问：** 注册表如何避免顺序不确定？一个插件阻塞会影响谁？

### Q12. 如何评测两个 Agent 引擎的行为是否等价？

**口述参考回答：** 不要求自由文本逐字一致，而是比较是否满足同一任务约束：回复事实、工具选择、参数、动作顺序、实际状态与安全规则，并比较耗时。项目建立日志评测引擎，自动生成 OpenClaw/PicoClaw 对照报告，支持单 Query 下钻回复、调用链和耗时；另有线上指标看板。文档记录差异定位由天级缩短到小时级，但 PicoClaw 线上样本较少，不能直接据此宣称全量用户效果已验证。

**材料依据：** R：双引擎评测与线上看板。

**待补充：** 必须补：自动判定规则、人工复核、样本构成与效果定义；不要只用 LLM 打分。

**继续追问：** 同一任务两种合法工具路径，算不算差异或失败？

## P1｜执行可靠性与兼容

### Q13. 工具超时了，但操作可能已经执行，你会怎么处理？

**口述参考回答：** 超时说明等待结束，不说明动作一定没执行。先区分未发送、已受理、执行中、已完成和状态未知，尽可能按请求标识或业务状态查询确认，再决定重试。设置绝对值通常更容易做幂等，增量动作重复执行可能累加。项目已记录统一回执、超时和取消；具体幂等键、执行台账或查询接口未在材料中展开，面试中应讲实际能力，未知状态下的重试策略属于设计方案。

**材料依据：** R：统一回执、超时和取消；通用原理。

**待补充：** 必须补：是否有请求标识、结果查询和执行端幂等能力。

**继续追问：** 查不到状态，又必须尽快响应用户怎么办？

### Q14. 用户中途取消或改了指令，如何处理正在运行的 Agent？

**口述参考回答：** 取消要贯穿任务队列、模型流和工具等待，先阻止新动作，再尝试取消下游执行；用任务版本隔离迟到结果。已完成动作不会因为结束生成自动撤销，是否恢复要看业务和用户意图。项目文档记录工具收发统一处理超时与取消，但下游是否可取消、用户改指令如何切换尚未展开。可按这套机制解释设计，再补实际实现，不能把推荐状态机说成已落地。

**材料依据：** R：取消能力；通用设计。

**待补充：** 必须补：实际取消传播、任务标识、迟到回包策略和不可取消工具。

**继续追问：** 取消之后旧回包到了，新任务会受影响吗？

### Q15. 如何让上层业务在更换引擎时尽量不用改代码？

**口述参考回答：** 在适配层保持消息协议、鉴权、工具名、Schema 和结果语义，内部重构不直接泄露给上层。项目通过 LiClaw Channel 与 Bridge 统一接入和路由，兼容已有业务协议与 ticket 鉴权，同时迁移业务 Tool/Hook。App 零改造不是所有代码零改造：引擎和业务插件仍有 Go 重构工作。验收需要用旧客户端和异常用例验证，不能只比接口签名。

**材料依据：** S、R：通信统一与业务兼容；E：迁移清单。

**待补充：** 必须补：你实际负责的协议适配、版本兼容和错误码处理。

**继续追问：** 协议不变，事件顺序或超时变了怎么办？

### Q16. 如何兼容存量 Skill，同时降低脚本运行开销？

**口述参考回答：** 把描述兼容、工具兼容和运行环境兼容分开。SKILL.md 格式相同不保证内部脚本和工具可用。一期优先复用现有容器与 Python/Node.js 环境，保持存量 Skill 代码和提示词使用方式；二期规划把适合的脚本改为 Shell/Go，逐步去除解释器依赖。只有在全量业务迁移后才能计算完整资源释放，不能把一期结果说成已剥离所有解释器。

**材料依据：** S：一期兼容与二期去解释器；E：Skill 分类。

**待补充：** 必须补：具体 Skill 数量与版本、脚本依赖、已完成改造和测试。

**继续追问：** Shell 会启动外部进程，为什么一定比原脚本快？

### Q17. 流式输出如何设计，如何避免丢片段或错误解析工具参数？

**口述参考回答：** 要区分文本、推理展示、工具参数增量和终止事件；按请求关联并保持必要顺序，处理背压、取消和异常结束。工具参数增量往往不是独立合法 JSON，应按协议积累，到完成事件再完整解析和校验。项目把处理收敛为 Go 单循环直解和回调累积，工具参数流结束后一次解析，减少多层分发。具体缓存上限与异常协议处理需根据实际实现补充。

**材料依据：** R：流式处理优化；通用协议原理。

**待补充：** 必须补：事件格式、参数分片、超限处理和部分断流用例。

**继续追问：** 流中断时已经积累的工具参数可以执行吗？

### Q18. 缓存 Prompt、工具定义和文件内容，如何避免读到旧数据？

**口述参考回答：** 缓存应明确键、版本和失效条件。配置、工具 Schema、Skill 文件或用户状态变化时，需要失效或生成新快照；一次请求内部尽量使用一致版本。评估材料讨论了变更后局部更新缓存，一期材料也包含热重载与模型热切换，但缓存失效、并发更新的一致性机制尚未展开。面试时应说明实际策略，并验证改配置、热更新 Skill 和并发请求等场景。

**材料依据：** E：缓存减少重复构建；S：热更新与模型热切换。

**待补充：** 必须补：实际缓存对象、版本、失效触发与一致性策略。

**继续追问：** 热更新发生在任务执行中，使用新版本还是旧版本？

### Q19. 如何灰度替换常驻引擎，出问题时安全回滚？

**口述参考回答：** 先明确切换粒度和生效时机，再保留旧引擎作为回退目标。根据进展材料，端侧引擎开关与双引擎启停已开发，切换经进程重启生效，支持启动失败自动回退；文档当时记录 A/B 策略预计随内测 2 验证。还要处理会话、未完成任务和已执行副作用，防止新旧引擎同时执行。启动失败回退不等于所有运行中错误都会自动回退。

**材料依据：** R：灰度与回滚图表、版本进展。

**待补充：** 必须补：当前最新发布状态、切换粒度、触发条件及状态迁移方式。

**继续追问：** 任务执行到一半切引擎，会不会重复车控？

### Q20. 怎样建设 Agent 可观测性，让问题能快速定位？

**口述参考回答：** 以任务、轮次、模型调用和工具调用为层级记录关联标识、时间、输入输出摘要、结果和错误，并保护敏感数据。项目迁移了 traceId 全链路追踪和遥测，日志评测支持单 Query 链路对照，看板比较任务量、完成率、耗时与调用指标。观察差异后应能归因到上下文、模型、工具或执行编排。监控本身也有资源开销，要限制日志体积和上报策略。

**材料依据：** E：traceId 与遥测迁移；R：评测和看板。

**待补充：** 必须补：实际 trace/span 结构、时间口径、脱敏与采样方案。

**继续追问：** 跨异步任务如何传播关联标识，避免串会话？

## P2｜原理补强与演进

### Q21. Go 为什么适合这类项目？它有哪些性能风险？

**口述参考回答：** Go 的编译部署方式和并发机制适合构建端侧常驻服务，也能减少原有 JS 依赖加载负担。但 Go 仍有运行时、GC 和调度器，并不保证更低内存或更短延迟。业务仍可能因高频分配、goroutine 泄漏、锁竞争、阻塞 IO 和无界队列出问题。应结合 heap/CPU profile、goroutine 和调度信息定位，而不是用语言名称替代性能证据。

**材料依据：** 通用原理；E 中语言对比只作选型背景。

**待补充：** 若你负责 Go 开发，本题及并发、取消、GC 应升为 P0；补真实代码案例。

**继续追问：** context 取消能强制终止 goroutine 吗？

### Q22. 为什么要把 Agent 的执行策略做成可插拔？什么时候用 ReAct 或固定流程？

**口述参考回答：** 任务差异决定执行方式：路径明确的任务适合确定性流程，需要探索的任务适合决策—工具—观察循环，对时延敏感的简单任务可以走单次快响应。项目二期规划把 agent 身份与 agent-loop 执行策略解耦，按 TaskType 路由，不匹配时降级到默认驱动器。接口需定义输入状态、输出事件、取消、预算和错误语义；这是二期规划，不能与一期已完成能力混写。

**材料依据：** S：二期 AgentLoop 插件化与策略路由。

**待补充：** 必须补：二期最新进度、实际接口和路由规则；Reflexion 不必用于所有任务。

**继续追问：** 路由错了或插件失败，回退会不会重复执行？

### Q23. 什么时候需要多 Agent，而不是一个 Agent 加工具？

**口述参考回答：** 只有独立权限、上下文边界、可并行子任务或不同执行角色带来可测收益时才拆。多 Agent 会增加调度、通信、Token 和恢复成本，在资源受限车端更需谨慎。材料记录 A2A 链路兼容和部分多 Agent 能力迁移，但不能据此推出所有车端任务都采用多 Agent。面试中先解释单 Agent 基线，再按真实场景比较收益和成本。

**材料依据：** S、E：A2A 兼容与能力覆盖；通用原理。

**待补充：** 必须补：你是否实际做过多 Agent 场景，避免把支持能力当业务使用。

**继续追问：** 简单多步任务为什么不用固定编排？

### Q24. 使用 AI 辅助框架迁移，如何保证生成代码没有改变业务行为？

**口述参考回答：** 先明确接口、行为约束和能力矩阵，把改造拆成可独立验证的小模块。对工具契约、事件顺序、安全检查和副作用进行回归，对性能改动做基准对照，并人工审阅关键并发与权限代码。项目已有模块化迁移规范和双引擎评测，可用来验证代码行为；但材料未说明你实际使用 AI 开发，只有真实使用过才讲工具、方法和收益。

**材料依据：** R：评测保障；S：模块化研发；通用开发建议。

**待补充：** 必须补：是否实际使用 AI、具体任务、发现的错误和验证过程。

**继续追问：** AI 为通过测试删掉安全检查，你怎么发现？
