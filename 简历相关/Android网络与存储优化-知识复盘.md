# Android 网络与存储优化 — 知识复盘

---

## 知识体系速查

### 网络

#### Radio 状态机

```
IDLE(休眠,~0mA) ──数据传输──→ DCH(全功率,~300mA) ──5~10s无数据──→ FACH(中功率,~100mA)
     ▲                                                                    │
     └──────────────────── 10~15s 无数据 ──────────────────────────────────┘
```

每次请求 Radio 尾部时间 **~30 秒**（DCH 10s + FACH 15s）。10 次 1KB 请求 = 300s 全功率 vs 1 次 10KB = 30s 全功率。

#### 连接复用

| 手段 | 效果 |
|------|------|
| Keep-Alive | 复用 TCP 连接，省握手 |
| HTTP/2 多路复用 | 一个 TCP 并行收发多请求，解决队头阻塞 |
| 连接池 | OkHttp 默认 5 个空闲连接，保活 5 分钟 |
| HTTPDNS | 绕过运营商 LocalDNS，防劫持+精准调度 |

HTTP/1.1 Keep-Alive vs HTTP/2 多路复用：

| | HTTP/1.1 Keep-Alive | HTTP/2 多路复用 |
|--|---------------------|-----------------|
| 连接 | 复用同一个 TCP | 复用同一个 TCP |
| 并发 | **串行**，上一个响应完才能发下一个 | **并行**，多个请求同时收发 |
| 队头阻塞 | 有 | 无（二进制分帧，独立流） |

#### 数据传输优化

| 方式 | 压缩率/优势 | 适用场景 |
|------|-------------|----------|
| Gzip | 70%~90% | JSON/文本 API |
| WebP | 比 PNG 小 30%+ | 图片 |
| Protobuf | 比 JSON 小 50%+，快 10x+ | 内部 RPC |
| 增量更新 | 只拉变化部分 | 列表数据 |

#### 弱网策略

图片降级 → 超时缩短 → 优先缓存 → 断点续传（Range 请求头）

### 存储

#### KV 存储对比

| 对比 | SharedPreferences | MMKV | DataStore |
|------|-------------------|------|-----------|
| 读写速度 | 基准 | **快 100 倍** | 中等 |
| 写入方式 | 全量重写 XML | 增量 append | 增量 |
| 跨进程 | 不支持 | 支持 | 可安全 |
| 底层 | XML + IO | mmap + protobuf | 协程 + Proto |
| 异步 | apply（不可控） | 同步但极快 | 协程 suspend |

#### SharedPreferences 四大问题

| 问题 | 说明 |
|------|------|
| 全量加载 | 首次 getXxx 把整个 XML 读到内存 |
| 全量写入 | 每次修改写整个 XML |
| apply 不可控 | onStop 时 QueuedWork.waitToFinish() 强制等待 |
| 不支持跨进程 | 无文件锁，多进程写丢数据 |

#### mmap 原理（MMKV 快的原因）

```
传统 IO:  用户空间 ──→ [copy] ──→ 内核空间(Page Cache) ──→ 磁盘   （两次 copy + 系统调用）
mmap:     用户空间 ←─直接映射─→ 内核空间(Page Cache) ──→ 磁盘      （一次 copy + 无系统调用）
```

三优势：**直接映射少一次 copy + 无系统调用开销 + 增量 append（非全量写）**

#### SQLite/Room 优化

| 手段 | 说明 |
|------|------|
| WAL 模式 | 多读一写并发，写不阻塞读 |
| 索引 | 查询字段加索引 |
| 事务批量 | 多操作合并为一个事务，只刷一次 |
| 预编译 | SQLiteStatement 复用 SQL 解析 |
| 分页 | LIMIT/OFFSET 避免全量加载 |
| FTS | 全文搜索用 FTS 虚拟表 |

## 问答复盘

### Q1: SharedPreferences 有哪些核心问题？apply 和 commit 的区别？apply 何时卡主线程？

**我的回答：**

SP 是全量读、全量写，不支持并发操作，使用 apply 异步也不可控。存大量数据时每次读写成本很高。apply 是异步，commit 是同步。当 apply 操作时阻塞 Activity onStop。

**点评：** ⭐⭐⭐⭐ 答得好

补细节：apply 阻塞 onStop 的具体机制是——Activity onStop 时系统调用 `QueuedWork.waitToFinish()`，**强制等待所有未完成的 apply 任务执行完**。数据量大时这个等待会卡几百毫秒。

**优化点：** 面试中说出 `QueuedWork.waitToFinish()` 机制，体现对 SP 阻塞原理的深入理解。

---

### Q2: MMKV 为什么比 SP 快？从 mmap 原理角度解释。

**我的回答：**

因为 MMKV 是基于 mmap 的，相比 SP，前者建立了用户空间到内核空间的映射，一次 copy，后者两次 copy。

**点评：** ⭐⭐⭐ 原理对，表述需精确

需精确化：
- 传统 IO：用户空间 → 内核空间（Page Cache）→ 磁盘，两次 copy + 系统调用开销
- mmap：用户空间直接映射 Page Cache → 磁盘，一次 copy，无系统调用（写内存即写文件）
- MMKV 还有一个关键优势没提到：**增量 append 写入**，SP 是全量重写 XML，MMKV 只追加变化的部分

**优化点：** 面试中说出三个关键词——**直接映射（少一次 copy）、无系统调用开销、增量 append（非全量写）**。

---

### Q3: 网络请求批量合并为什么能省电？

**我的回答：**

合并请求只有一次请求。省在网络唤醒时 IDLE → 全功率 → 半功率只有一次；多次请求多次唤醒。

**点评：** ⭐⭐⭐⭐ 完全正确

补数字更有说服力：每次请求的 Radio 尾部时间是 **~30 秒**（DCH 10s + FACH 15s），10 次请求 = 300 秒全功率 vs 1 次 = 30 秒全功率。

**优化点：** 面试中说出"30 秒尾部时间"这个数字，量化收益。

---

### Q4: OkHttp 连接池机制？HTTP/2 多路复用和 HTTP/1.1 Keep-Alive 的区别？

**我的回答：**

OkHttp 连接池会复用 TCP 连接，少了 TCP 握手的消耗。HTTP/2 多路复用，一个 TCP 连接可以并行发送多个链接。

**点评：** ⭐⭐⭐ 基本对，多路复用描述有误

问题在 HTTP/2 多路复用的描述：
- "一个 TCP 连接可以并行发送多个**链接**"——应该是"多个**请求**"
- 更关键的区别没答到：

| | HTTP/1.1 Keep-Alive | HTTP/2 多路复用 |
|--|---------------------|-----------------|
| 连接 | 复用同一个 TCP | 复用同一个 TCP |
| 并发 | **串行**，上一个响应完才能发下一个 | **并行**，多个请求同时收发 |
| 队头阻塞 | 有（响应慢的阻塞后续） | 无（二进制分帧，独立流） |

**优化点：** HTTP/2 多路复用的核心是**并行收发 + 解决队头阻塞**，不只是"一个连接发多个请求"。

---

### Q5: SQLite/Room 核心优化手段？WAL 解决什么问题？为什么批量插入用事务？

**我的回答：**

SQLite：分页，建库时添加索引，批量插入用事务。Room：批量插入用事务。WAL 解决了写时无法读取的问题，可以实现 1 个读和多个写。单个插入也是事务，经历写入-commit-刷表过程；批量插入用一个事务，只刷一次。

**点评：** ⭐⭐⭐ 方向对，WAL 描述有误

✅ 分页、索引、事务批量——正确。
✅ 单条插入也是事务、批量用一个事务只刷一次——**非常准确**。

WAL 描述有误：
- "可以实现 1 个读和多个写"——**反了**。WAL 是**多个读 + 1 个写**可以并发。
- WAL 解决的问题：传统模式下**写操作会锁表，读操作被阻塞**。WAL 模式下写入先写到 WAL 日志文件，不直接修改主数据库，**读操作读主库不受写阻塞**。

补充 SQLite 优化漏了的：
- **预编译 SQLiteStatement**：复用 SQL 解析
- **FTS 全文搜索**：文本检索用 FTS 虚拟表

**优化点：** WAL 是"多读一写并发"，不是"一读多写"。面试中别说反。
