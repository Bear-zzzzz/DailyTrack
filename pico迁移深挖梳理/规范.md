# 项目描述与深挖问答规范

## 1. 目标

让简历内容、口述回答和实际证据保持一致。先建立项目主线，再通过面试官视角的追问检验个人技术深度。问题根据岗位与能力考察设计，项目文档用于支撑回答，不按文档段落逐条出题。

## 2. 固定协作流程

1. 选题：确定题号、题型和口述时长。
2. 用户作答：逐字保存原始回答，不先替用户改写。
3. 评价：先给总分，指出回答已完成什么，再列最多三个主要问题。
4. 建议：指出具体句子该如何改、为什么改；分清表达问题、原理错误、事实错误和证据不足。
5. 优化稿：保持用户已确认的职责边界，不加入未确认的实现或成果；明确为助手候选稿。
6. 同步：写入题目文件，更新概览与当前进度。未经用户确认，优化稿不标为采用稿。
7. 复答：用户重新回答时建立新版本，评分并比较实际改善；复答不覆盖旧版本。

用户只要评分与建议时，先评价原答；优化稿按需要提供，不能用改写替代评价。用户仅提出事实纠正时，追加说明并更新事实依据，保留原答与当时评价。

## 3. 回答结构

| 题型 | 推荐结构 | 首轮长度 |
|---|---|---|
| 项目介绍 | 场景与问题 → 目标 → 个人职责与关键做法 → 项目效果 | 45–90 秒 |
| 原理与选型 | 结论 → 核心机制 → 适用条件与取舍 → 项目例子 | 1–2 分钟 |
| 项目深挖 | 具体问题 → 我的决策与实现 → 难点与异常 → 验证与代价 | 2–3 分钟 |
| 场景设计 | 澄清前提 → 正常链路 → 异常与边界 → 取舍 → 验证 | 3–5 分钟 |
| 性能与评测 | 基线及口径 → 定位方法 → 改动 → 对照结果 → 限制 | 2–3 分钟 |

项目介绍不要求一次讲完架构。用一个确实做过的技术点引出深挖，避免罗列名词。场景建议和二期规划不能写成已实现能力。

## 4. 评分规范（10 分制）

评分是本次回答质量的练习反馈，不是实际录用概率。按题型评价，不因一分钟介绍未展开所有细节扣分。

| 维度 | 分值 | 考察 |
|---|---:|---|
| 场景、目标与问题理解 | 2 | 是否切题，说明问题为何重要；设计题是否澄清前提 |
| 个人贡献或技术机制 | 3 | 项目题能否区分职责；原理题能否解释机制；场景题是否可执行 |
| 结果、验证与证据 | 2 | 指标口径、对照条件、成功条件及限制是否清楚 |
| 结构与口述表达 | 2 | 顺序、重点和时长是否适合当前题型 |
| 事实准确与边界 | 1 | 是否混淆均值/峰值、个人/团队、目标/结果、规划/落地 |

- 9–10：主线完整、技术和证据充分，能应对关键追问。
- 8–8.5：清楚且有具体内容，仍有部分证据或深挖点需要补齐。
- 7–7.5：基本主线成立，职责、技术机制或验证较概括。
- 6–6.5：可理解，但存在明显结构缺口或重要事实、机制问题。
- 低于 6：需要重建主线或校准核心认识。

新评价记录各维度分数与理由，总分按 0.5 分粒度表达。Q01 V01 为此前已给出的历史总分，保留原评分，不补造当时不存在的分项记录。不能为了体现进步自动提高分数。影响核心结论的事实错误需明确指出，并将相关结论标为待核实。

助手优化稿可以评分，但评价的是文本质量；未经用户复述，不能视为用户能力提升或练习完成。明确写出仍然缺失的技术细节。

## 5. 版本规则

- 每题独立使用 V01、V02……，按记录顺序递增。
- 作者必须标为“用户原答”“用户复答”或“助手候选稿”；参考素材不占用回答版本号。
- 每个回答版本都记录总分、评价、建议、采用状态；待评价版本明确标记，不填伪造分数。
- 用户原答保留错字与原始措辞。改写、事实修正和补充放在独立字段。
- 状态区分：未作答、已评价待复答、候选稿待 review、用户已采用、待复测。
- 概览记录“最近用户作答”和“候选稿”两个位置，避免只展示助手最高分版本。
- 历史版本不覆盖；用户要求修改或删除历史时按其要求处理。

## 6. 每次评价模板

```text
题号 / 题型 / 目标时长：
版本 / 记录日期 / 作者 / 状态：
原始回答：
总分与分项：
做得好的地方：
主要问题（最多三项）：
具体优化建议：
事实校准与待补证据：
继续追问（1–3 个）：
与上次用户版本的变化：
采用状态 / 下次复练重点：
```

优化稿作为新版本保存，可引用原版本的问题与建议。不同作者之间不当成用户复答的进步比较。

## 7. 简历与材料同步规则

- 简历草稿只写已确认的职责与成果；“主导”“独立完成”等措辞需有用户事实支持。
- 项目整体性能收益与个人工作的关系需要解释，不直接把整体百分比归因于个人模块。
- 只有用户确认的回答能作为采用稿；不得自动覆盖实际简历。
- 项目事实与指标在“素材依据”集中维护，回答引用时记录口径。
- 新资料可修正事实和后续评价，但不悄悄修改此前原答。

## 8. Review 重点

每次最多集中处理三个问题，优先顺序：事实准确 → 职责与机制 → 验证证据 → 表达压缩。不得为了答案显得完整补造实现、数据或故障经历。
