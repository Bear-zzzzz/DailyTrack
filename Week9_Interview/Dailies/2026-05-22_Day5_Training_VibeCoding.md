## 🧠 模块 1：Agent 完整分层架构（阿里 Q1）

### 5 层架构

```
Layer 1：任务入口层
  接收用户问题和上下文

Layer 2：决策层
  意图识别 → 任务拆解 → 规划 → 工具选择

Layer 3：执行层
  真正调工具 / 查知识库 / 访问服务

Layer 4：记忆和状态层
  管理多轮上下文 / 历史结果 / 中间变量

Layer 5：验证层（可选）
  执行前后校验（参数有效性 / 结构完整性 / 结果一致性）
```

**核心挑战**：
> 不是"能不能思考"，而是"能不能稳定执行"

## 🧠 模块 2：RAG 离线 + 在线完整实现（阿里 Q2）

### 离线部分（建库）

```
文档清洗 → 分块 → 去重 → embedding 计算 → 向量数据库建索引
                  ↑
          每块附元数据：标题 + 章节路径 + 来源
```

### 在线部分（检索）

```
用户 query
  → 编码成向量
  → 向量库检索（ANN）+ BM25/关键词并行召回
  → rerank 模型重排
  → 组装 top-k 相关证据
  → 送给 LLM 生成答案
```

**核心结论**：
> RAG 最终效果不只取决于向量，还取决于分块设计 + 召回策略 + 重排质量

## 🧠 模块 3：预训练数据清洗（阿里 Q3）

### 三类问题数据

```
① 脏数据
  乱码 / HTML 残留 / 脚本片段 / 异常符号 / 编码错误

② 重复数据
  精确重复 + 近似重复

③ 低质量数据
  广告 / 无意义填充 / 模板文本 / 机翻片段 / 损坏文本
```

### 三步清洗流程

```
Step 1：规则清洗
  去 HTML 标签 / 过滤控制字符 / 长度约束 / 语言检测

Step 2：质量过滤
  困惑度过滤（PPL 高的文本质量差）
  分类器识别垃圾文本
  关键词规则

Step 3：去重
  MinHash / SimHash / LSH 近似去重
```

**核心结论**：
> 真正影响模型上限的，往往不是架构，而是预训练数据质量

## 🧠 模块 4：Agent 工具调用训练集构建（阿里 Q5）

### 训练样本三类

```
① 应该调用的案例（正例）
② 不该调用的案例（负例）← 容易被忽略
③ 需要多工具顺序调用的案例
```

### 数据来源四种

```
① 人工标注轨迹
② 线上高质量人/系统交互日志
③ 规则合成数据
④ 强模型自生成轨迹 + 人工校验
```

**关键挑战**：
> 缺参数、工具空返回、多工具场景的处理优先级很重要
> 否则模型容易过拟合或上线后乱调

## 🧠 模块 5：构造数据集三大难点（阿里 Q6）

### 难点一：合成/真实数据不匹配

**现象**：人工数据太标准化，参数过于齐全，上线后用户没说全意图就崩

**解法**：
- 导入真实线上 query
- 按意图 / 复杂度 / 缺参数 / 歧义性分类
- 针对性补齐边界样本

### 难点二：标注不一致

**现象**：同一问题，不同人标成不同工具

**解法**：先统一 schema 和决策标准，再开始标注

### 难点三：短尾样本少

**现象**：低频场景数据不够，模型不会处理

**解法**：
- 模板改写
- 对抗生成
- 人工标注边界案例
- 优先补充高风险失败点

## 🧠 模块 6：LoRA vs 全参数微调（阿里 Q7）

### 对比

| | LoRA | 全参数微调 |
|---|---|---|
| 原理 | 在原权重层附近插入低秩矩阵，只训练少量新参数，冻结原模型 | 直接更新所有参数 |
| 内存占用 | 低 | 高 |
| 训练速度 | 快 | 慢 |
| 多任务切换 | 容易（换 LoRA adapter 即可） | 难 |
| 适合场景 | 格式对齐、指令跟随、工具使用 | 需要深度改变模型能力 |

**选型原则**：
- 改格式、改风格、让模型学会调工具 → LoRA
- 需要从根本上提升模型能力 → 全参微调

## 🧠 模块 7：PPO / DPO / GRPO（阿里 Q8）

### 三者核心区别

**PPO**：
- 策略梯度方法
- 需要奖励模型给输出打分，再更新策略
- 训练路径长，超参敏感，稳定性中等

**DPO**：
- 直接偏好优化
- 用 chosen/rejected 配对，直接优化策略
- 无需采样和奖励模型，工程最简单

**GRPO**：
- PPO 的扩展，从 pairwise 泛化到 groupwise
- 利用多个候选之间的相对偏好
- 天然适合排序任务和多样本比较

### 对比总结

| | PPO | DPO | GRPO |
|---|---|---|---|
| 数据形态 | 轨迹 + 奖励分数 | chosen/rejected 配对 | 多候选组 |
| 是否需要奖励模型 | 需要 | 不需要 | 不需要（或内置） |
| 工程复杂度 | 高 | 低 | 中 |
| 适合场景 | 通用 RLHF | 偏好对齐，快速迭代 | 排序、多样本比较 |

**核心区别不只是公式**：
> 三者最大区别是数据形态 + 训练稳定性 + 适用任务范围

## 🧠 模块 8：Vibe Coding 面试四步法

### 核心观点

> 面试官想看的不是 AI 有多聪明，而是你作为"架构师"的思维过程
> AI 只是你的高级键盘，技术选型必须由你来决定

### 四步框架

```
Step 1：定边界和骨架（展现全局观）
  先定数据结构和模块接口
  Prompt："请先不要写业务逻辑，只帮我定义核心类的 Interface 和骨架"
  目的：谋定而后动，防止 AI 生成结构失控

Step 2：选择并指挥核心模型（展现技术掌控力）
  明确技术选型理由，告诉 AI 用什么组件
  Prompt："为了防止 OOM，请使用 ArrayBlockingQueue 作为底层缓冲队列"
  目的：AI 是键盘，技术选型是你做的

Step 3：攻克难点（展现深度思考）
  单独抽出极端场景让 AI 解决
  Prompt："当队列满时，请实现带超时机制的阻塞重试逻辑"
  目的：展现你对复杂场景的预判能力

Step 4：兜底与测试（展现工业级标准）
  加优雅停机 + 并发测试用例
  Prompt："请加上 Graceful Shutdown，并生成 100 线程并发压测用例"
  目的：证明这是能上线的代码，不是玩具
```

### 面试时的关键动作

> 把自己的 Prompt 解释出来——面试官看不到你脑子里的想法，要主动说出你为什么这样写
