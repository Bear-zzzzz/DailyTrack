# 面试问答梳理

---

## 一、RAG 与检索管线

**Q1: 三层插件化 ReAct 架构中，Domain 层和 Skill 层的边界怎么划分？**

**A:** Domain 层加载对应排查领域的配置文件，配置文件中包含可激活的 Skill、Tool，也可指定该领域的排查指引 Prompt。新增一个 Domain 时选择可激活的 Skill，Skill 和 Tool 都是可复用的。

**优化点：** 表述偏静态，可补充"新增一个 Domain 从配置到上线的时间成本"，以及"现有的 Domain 和 Skill 数量级"（如 5 个 Domain、20+ Skill），体现规模感和复用收益。

---

**Q2: Hybrid RAG 具体怎么混合的？检索了哪些数据源，权重/排序策略？**

**A:** 小模型意图识别 → 决定直接回答还是走 RAG → 小模型做子问题拆分 → 并行混合检索 → 结果重新打分：


| 参数     | 代码检索          | 经验检索 |
| -------- | ----------------- | -------- |
| 召回数量 | 10 条             | 5 条     |
| 混合权重 | 0.6 FTS + 0.4 Vec | 同       |

→ Rerank 取 top-k，阈值 0.35（8B 模型上 0.3 视为完全无关）→ 融合注入 Prompt。

代码 RAG 预处理：清洗配置/test/demo/SDK 等无意义内容；关键链路做标注。Chunk 策略：按文件/模块切分，保留完整函数，chunk 头部注入文件路径、类名、函数名作为前缀。

Embedding：kivy-qwen3-embedding-0_6b。

数据库 schema：project_id、版本、仓库路径、类名、开始行、结束行、函数名、向量值 blob、chunk_text。

**优化点：**

- 子问题拆分 vs 不拆分缺乏消融实验数据，面试官追问"拆分到底带来多少增益"会被动，建议补一个量化的 A/B 对比结论。
- "清洗无意义内容"的具体实现（正则硬规则 or 模型判断）需明确，避免被追问陷入细节盲区。
- Rerank 阶段除了向量/关键词，metadata（路径、类名、摘要）是否参与打分没讲清楚，建议明确"rerank 模型输入包含结构化 metadata"这个亮点。

---

**Q3: 25% 未覆盖的 case 主要卡在哪里？**

**A:** 分三类：① 自动化排查出了结果但人工校验结论偏离；② 超过最大 30 轮终止；③ 描述不清晰、条件不足无法排查。

**优化点:** 三类未覆盖 case 的占比没给，建议补上数值（如"结论偏离占 10%（高置信度陷阱，人工抽检发现），超轮次占 8%，描述不清占 7%"）。另外对于占比最高的类别，是否有针对性优化，要准备回答。

## 二、Agent 引擎与安全控制

**Q4: 最大 30 轮终止是硬限制吗？有没有 early stop 机制？**

**A:** 30 轮可配置。每轮结束时检查置信度，若 >90% 则提示尽快收敛给出结论。

**优化点:**

- **置信度来源是致命问题**——LLM 自评还是独立 evaluator？如果是 LLM 自评，"模型自信但错误"是已知可靠性隐患。建议明确回答来源并准备好应对方案（如或"高置信度 case 回流人工抽检"）。 后期 ->"独立 evaluator 模型交叉校验"
- 30 轮中被终止的 case 在哪个轮次附近开始无效循环？有没有分析过？主要是问题复杂，难以排除，比如是应用启动时问题，导致初始化存在问题，这种情况下log需要拉取更多。

**Q5: 工具调用失败的重试策略和降级链路？**

**A:** 单工具最多重试 3 次，同时尝试使用别的工具替代，并发送告警让人工介入。

**优化点:** 告警后人工介入的 SLA（响应时间、升级机制）没讲。替换工具的优先级策略（如"先找同类工具 → 降级到经验库 → 兜底提示人工"）可以讲得更清晰，体现降级链路的层次感。

## 三、评测体系

**Q7: 评测维度树的具体结构？怎么归因？**

**A:** 四级树形结构，覆盖 13+ 子指标：

```
一级：任务可用率
├── 二级：协议准确率
│     ├── conditionType 准确率
│     ├── actionType 准确率
│     ├── 条件参数准确率
│     └── 动作参数准确率
├── 二级：呈现准确率
│     ├── 回复确认准确率
│     ├── 标题准确率
│     └── icon 准确率
├── 二级：拒绝合理性
│     ├── 误拒绝率
│     └── 漏拒绝率
└── 二级：体验质量
      ├── 回复自然度
      ├── 标题简洁性
      ├── 文案质量
      ├── 幻觉率
      └── P95 延迟
```

归因链路：三级漏斗——代码规则判断 → LLM 语义判分 → 人工复核，Bad Case 经漏斗落位后归因至 Prompt / 流程等来源。

**优化点:** 这个回答是全场最佳。树形结构清晰，漏斗层次合理。可额外准备：新增一个指标维度的工作量（代码层 +1 行、LLM 层 +1 示例，已讲了），以及**规则冲突怎么检测**（比如协议通过但呈现失败时，算谁的？）。

---

**Q8: 代码判断层规则有多少条？怎么维护？**

**A:** 代码规则层 +1 硬编码；LLM 语义校验层 +1 示例。

**优化点:** "加一个"是单位成本，但现有规则总量没说。建议补充："目前代码规则约 X 条，覆盖 Y 类常见错误模式"，体现规模感。另外规则多了之后的优先级、冲突检测机制可准备。

---

**Q9: 1000+ 评测集如何保证不"过拟合"？**

**A:** 对已有case坐同义改写，参数替换，团队内部试用发现的 bad case 也随时沉淀进去

## 四、VLA 语音控车

**Q10: 多级 Filter 具体有几层，在什么节点拦截？**

**A:**



【第1段 · 安全层】— 涉及人身/车辆安全的硬阻断，不可绕过
├─ 主驾校验       → 非主驾发声直接拒绝，防止副驾/后排误触发
├─ 泊车运行保护   → APA 运行中禁止新指令，避免运动中的车辆响应冲突
└─ 无人指令门槛   → getoff/getoff_park 需 VLA 召唤开关开启

└─ 车辆物理状态 → 任意车门未关

【第2段 · 功能路由层】— 按 domain/command 分发到对应子流程
├─ 选择车位子流程     ├─ 泊车免唤醒子流程
├─ APO 泊出子流程     ├─ 泊出子流程
└─ 每个子流程内置 isParkCommandAllowed() 二次校验

【第3段 · 能力判断层】— 跨 Store 状态匹配，前置条件汇总
├─ 车型能力     → Pro 车型在功能路由之后统一拦截
├─ 功能开关     → VLA 指挥总开关
├─ 场景状态     → 行车/AVP/漫游/长时任务的综合状态机**优化点**


第4段：敏感场景二次校验机制，比如开启智驾功能

---

**Q11: 弱网/中断场景怎么处理？**

**A:** 未收到 AD 状态回执 → 返回语音 fail 指令。

**优化点:** 策略正确但单薄。可补充：是否有超时配置（如 N 秒无回执即 fail）、是否有本地兜底（如端侧缓存上一次有效状态做乐观执行）、弱网占比和 fail 率的数据。

---

**Q12: VLA 项目中你具体写了多少端侧代码？**

**A:**


协议定义

- 定义了 EID ↔ Copilot ↔ AD 三端的指令协议：ai_driver 域 42 条命令 + parking 域 12 条 + 5 条全局控制指令
- generateCombinedDcc() 将语音指令封装为 AD 能消费的 JSON，携带 domain/command/content/dialogId/VAD 时间戳等 10 个字段
- formatDcc() 做语义归一化——NLU 下发的模糊 park 指令根据 content 中的 target 自动映射为 park_in/park_out/park_side
- RegisterSceneParams 定义 9 种场景，每种有独立的白名单指令集


状态机

舱外/眼镜链路实现 6 状态 × 12 事件的有限状态机（MachineBootFlowReducer，396 行）：

Idle → Prechecking → PoweringOn → ADBooting → ADBootFinish

每个状态对同一事件有不同分支。关键设计：在 PoweringOn/ADBooting 状态中仍可接收新指令并二次校验；PowerOnOk 时若 FSD 已启动完成则跳过 ADBooting 直达 ADBootFinish。

异常恢复

- AD 启动 40 秒超时 → Abort + 播报失败 TTS + 写 VSS 状态码
- 车辆上电 2 秒超时 → 根据 31 种 quitReason 映射对应 TTS
- 场景注册失败 → 5 秒后自动重试
- 语音回复 7 秒超时 → 播报"当前网络不太好呢" + 清理队列
- 下电事件在任意非 Idle 状态可触发，回 Idle

长时任务状态流：NONE → NEED_CONFIRM → CONFIRM，区分 NLU 和 Agent 两路来源。

## 总结：面试准备优先级


| 优先级 | 待补充项                                   | 风险               |
| ------ | ------------------------------------------ | ------------------ |
| 🔴 高  | 置信度 >90% 的来源（LLM 自评 or 独立模型） | 一问倒             |
| 🔴 高  | 组件复用关系的量化（引擎复用率、接入成本） | 简历写了但说不清   |
| 🔴 高  | VLA 端侧代码的技术深度（不是"透传"）       | 可能被质疑含金量   |
| 🟡 中  | 子问题拆分 vs 不拆分的消融数据             | 追问检索质量时触发 |
| 🟡 中  | Checkpoint 粒度与恢复机制                  | 简历亮点变为盲区   |
| 🟡 中  | 三类未覆盖 case 的占比和优化策略           | 体现复盘能力       |
| 🟢 低  | 评测规则总量、版本波动率、弱网超时配置     | 锦上添花           |
