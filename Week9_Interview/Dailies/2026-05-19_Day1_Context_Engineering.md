## 🧠 模块 1：Skill 动态注入策略（腾讯 Q1）

### 问题
项目里是把 skill 直接塞进 system prompt 的，如果 skill 太多，占用上下文窗口太大，怎么处理？

### 核心答案

**问题根源**：所有 skill 直接嵌入 system prompt 的三个副作用：
- 上下文空间占用大（token 浪费）
- 候选选择时噪音高
- 模型在选择 skill 时容易混淆

**解决方案（三层架构）**：

```
① 外部 Skill 注册表
   System Prompt 只保留：最小规则 + 调用协议
   不在 prompt 里硬编码 skill 描述

② Skill Routing（按需注入）
   先做一层路由：规则 / 分类模型 / 向量搜索 → 筛选 top-k skills
   再注入：描述 + 参数 schema + few-shot 示例

③ 摘要版 + 完整版分离
   默认注入摘要版
   模型决定调用后 → 再加载详细说明（完整版）
   → 显著压缩 token
```

**记忆口诀**：注册表 → routing → 摘要/完整分层

## 🧠 模块 2：相似 Skill 消歧方案（腾讯 Q2）

### 问题
如果两个 skill 实际内容不一样，但是 description 很相似，导致 agent 每次加载错 skill，怎么解决？

### 核心答案

**根本原因**：description 相似时，单靠自然语言匹配很容易误召回，需要增加更强的判别信息。

**四步解决方案**：

```
步骤 1：结构化定义升级
   从纯文本描述 → 结构化定义，包含：
   • 适用场景（什么时候用）
   • 禁止场景（什么时候不用）← 关键！
   • 输入参数 + 返回格式
   • 前置条件 + 失败条件
   • 调用示例

步骤 2：两阶段选择
   先召回 top-k → 再让模型根据参数约束和示例做 rerank

步骤 3：增加负样本示例
   明确告诉模型：哪些问题不应该触发该 skill

步骤 4：执行前校验
   做 schema 校验 + rule check
   选错就中断，防止误调用扩散
```

**终极方案**：如果两个 skill 定义语义确实接近 → 合并成一个统一 skill，内部用参数路由，而不是在 prompt 里制造歧义

## 🧠 模块 3：上下文工程核心原则（腾讯 Q3、Q4）

### 问题 Q3
Agent 设计里你觉得最重要的部分是什么？

### 核心答案

**上下文工程（Context Engineering）**

> Agent 是持续决策系统，不是单轮问答。模型能否稳定执行，取决于信息如何被组织和优先级。

**核心原则**：
- "给模型正确的信息"，而不是"给模型更多的信息"
- 上下文工程做好 → 模型成为可控执行者
- 上下文工程做差 → 目标漂移、工具误用、记忆污染、推理错误

---

### 问题 Q4
上下文工程有哪些要注意的点？

### 5 条核心注意点

```
① 角色分离与上下文隔离
   system / developer / user / tool output / memory 严格区分
   外部文本和系统规则不能混用

② 信息过滤与上下文裁剪
   只保留当前任务相关内容
   历史对话、搜索结果、工具文档中无关内容全部排除
   目的：避免模型认知过载

③ 格式控制与结构化输出
   工具输出 → JSON
   任务状态 → 独立文本段
   历史 → 摘要，而非原文
   尽量用结构化格式替代自然语言描述

④ 可信度层次与来源分层
   系统规则 > 用户输入 > 工具结果 > 模型预测 > 知识证据 > 未验证生成
   ↑ 这个顺序很重要，面试必背

⑤ 长任务管理
   做文本压缩和过期过滤
   避免状态漂移和旧信息干扰新决策
```

## 🧠 模块 4：Tool vs Skill 的本质区别（腾讯 Q9）

### 问题
你怎么理解 Skill，和 Tool 的区别是什么？

### 核心答案

| | Tool | Skill |
|---|---|---|
| 定义 | 原子能力 | 稳定能力模块 |
| 例子 | 查数据库、读文件、发请求 | "审阅合同风险"、"整理会议纪要" |
| 组成 | 单一操作接口 | 多个 Tool + 工作流策略 |
| 边界 | 最低层操作 | 包含任务边界、输入输出约束、错误处理逻辑 |
| 复用性 | 低（原子，不带上下文） | 高（封装了业务场景） |

**工程视角**：
- 只暴露 Tool：模型每次重新组合，稳定性差
- 封装成 Skill：模型在更高抽象层操作，方便版本管理和效果评估

## 🧠 模块 5：Tool Calling 工程四层架构（腾讯 Q10）

### 问题
Tool Calling 一般怎么做，和普通函数调用有什么区别？

### 本质区别

| | Tool Calling | 普通函数调用 |
|---|---|---|
| 驱动方 | 模型决策驱动 | 开发者硬编码 |
| 控制权 | 宿主系统决定是否执行 | 开发者完全控制 |
| 需要什么 | 额外的校验和编排层 | 无额外层 |

### 工程四层架构

```
Layer 1：工具注册层
   管理工具的定义和元数据

Layer 2：参数 schema 层
   定义和校验参数格式

Layer 3：执行器层
   实际执行工具调用

Layer 4：审计日志层
   记录调用链路（用于排查和回放）
```

### 生产环境注意事项（面试重点）

> 模型只能输出候选调用，不能直接给模型工具执行权限！

服务端必须做：
- 白名单校验（工具名）
- 参数校验（类型、范围）
- 超时控制
- 限流
- 错误封装
